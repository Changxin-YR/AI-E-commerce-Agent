## 0. 产品定位、优先级与版本沿革

### 0.1 历史沿革：V0.4 相对 V0.3 的六项实质修订（完整保留）

| 第二轮外部评审问题 | 处理决定 | V0.4 解决方式 |
|---|---|---|
| P0 数据底座负担过重 | **采纳并明确最小范围** | CSV/Excel 成为 P0 正式入口；商品、订单、订单行、库存、客服消息只维护支持四条 MVP 所需的最小字段；不以 ERP 接口、同步、多仓交易逻辑为前提。详见第 21 节。 |
| P0 看起来只是 BI + 草稿 | **采纳，但不默认向真实买家自动发信** | 验收必须包含 AI 的多步技能选择、持久化待办/草稿/审批，以及一个在卖家控制的外发通道里确证成功的受控外部动作；自动回复真实买家需满足渠道授权与新鲜物流事实，默认留在 P1。详见第 14、22 节。 |
| E2E 与 MVP 没有关联 | **完全采纳** | 四条 MVP 直接映射长期 E2E-01—07，标明 P0 最小切片与未包含动作，防止误把七条全部当首版范围。 |
| 固定技能与流程不够 Agent 原生 | **采纳，并避免过度工程化** | P0 技能具备输入/输出/权限/副作用声明，工作流具备最小执行、分支、审批与恢复语义；LLM 受控选择技能而不是自由写业务状态，无须先开发通用技能市场/可视化流程编辑器。 |
| API 授权限制可能阻断 | **完全采纳** | 首次使用正面告知“文件导入可以完成 P0 分析，无法直接实时操作平台”；真实 Shopify/Amazon/TikTok 等接入转入 P1+，按操作验证。 |
| 自然语言问数与 MVP-04 优先级矛盾 | **完全采纳** | SO-057 从 P1 调整为 P0，限定为只读可信指标问答、显式口径和缺失拒答。P0/P1/P2 分布由 22/27/25 调整为 **23/26/25**。 |

**总原则：** `SO-001—SO-074` 功能全集和 `E2E-01—E2E-07` 长期闭环均保留；P0 只实现每个相关模块支持四条 MVP 的最小子功能。不把优先级调整误写为删除功能。竞品参考是需求依据，不代表 SoloOps 已具备相同运行成熟度。

### 0.2 产品的核心定位

- **核心产品是 AI Agent 运营自动化层**：接受运营目标、读取被授权数据、检测问题、组织多个受控技能、执行许可的动作、确认实际结果并生成复盘。
- **ERP 功能是业务支撑，不是独立卖点**：商品、订单、库存、仓储、物流、结算等长期需求不删除，但首版优先通过平台现有能力、经过授权的 ERP API、CSV/Excel 导入以及最低限度的本地业务记录获得数据；不能因为“ERP 基础”就丢掉 Agent 的真实业务操作对象。
- **用户依然是个人卖家**：不扩展为多租户收费平台、大型制造商系统或通用客服 SaaS。
- **“功能全集”与“当前版本的交付范围”严格区分**：SO 编号记录长线需求；P0/P1/P2 指优先级，不能用 P2 等同于“删除”。

### 0.3 优先级解释

- **P0｜首个可验收 MVP**：以 CSV/Excel 正式导入为起点，完成四条最小运营闭环所需的 Agent、最小业务数据、受控执行、结果存档与审批；不要求真实电商平台 API、不要求建立 ERP 完整业务模型，P0 中每个 SO 仅交付明示的最小切片。
- **P1｜完善为可用的个人卖家 V1.0**：在实际授权与政策允许条件下连接一个真实电商平台，补充真实数据同步、对外客户消息自动化和可控平台写入；继续拓展业务功能。
- **P2｜需求保留、后续扩展**：复杂跨平台与供应链、多媒体高级生产、达人营销、第三方技能生态、移动端和买家端功能。

**优先级是用户价值和闭环顺序的建议，不是工期估计，不构成接口可用承诺。**

### 0.4 项目实现状态单独记录

每个功能未来验收时至少区分以下状态：`未实现`、`合成数据本地通过`、`用户导入数据本地通过`、`经授权外部通道写入已确认`、`真实电商平台只读已验证`、`真实电商平台写入已确认`、`受账号资质或平台权限限制`。**邮件等外部通道写入不等于电商平台写入；导入真实文件不等于实时同步。** 状态与 P0/P1/P2 独立，验收必须指向具体证据。

## 1. 第一中心：AI 运营指挥中心

### SO-001｜个人卖家初始化与经营资料【P0｜业务支撑】
- 创建个人经营档案；记录目标国家/市场、经营模式、主营类目、常用货币、时区、默认语言、允许使用的店铺及平台。
- 通过人工录入、授权同步或导入文件初始化商品、库存、订单、成本和客服规则；展示未完成的初始化事项与数据缺口。
- **P0 必须提供 CSV/Excel 模板、导入预览、字段说明、错误行报告与按批次重导入；首次使用说明文件导入不是“低配补救方案”，而是 P0 正式业务入口。** 支持在只有商品+订单行数据时先运行适用的分析，缺其他数据时跳过对应功能而非补造。
- 提供新手任务示例与分步骤首次使用指引；不要求新手先配置全部自动化规则才能使用基础功能。
- **V1.0 补充——导入向导必须可用：** 文件上传后允许自动建议报表类型/字段映射，用户可查看原字段→目标字段、数据类型、示例值与映射置信度，并在确认前调整；保存个人映射模板供下次复用。不得强迫用户手改源文件列名。详见第 25 节。

### SO-002｜跨店铺经营总览与运营日报【P0｜业务支撑】
- 按店铺、平台、国家、日期汇总销售额、订单、退款、预估/已确认利润、待发货、库存预警、客户消息和营销表现；显示数据来源、更新时间、统计币种。
- 对比前日、近七日、近三十日及自选区间；展示热销商品、低利润商品、异常订单与待办；生成日、周、月经营摘要。
- 所有经营指标可进入来源明细；数据缺失时显示“未获取/未结算”，不能补造数值。
- **P0 统计仅基于导入数据覆盖的店铺、币种与时间窗；不得称“实时销售额”或“全渠道经营”。** 用户能从总览回到原始导入行与对应文件批次。
- **V1.0 补充——数字可解释：** 经营指标、异常结论与建议中的事实部分需提供“查看依据”，能查看统计口径、数据覆盖区间、导入批次、实际订单行及成本计算步骤；来源不充分的结论标记待核对。

### SO-003｜自然语言 AI 运营总控【P0｜Agent 原生】
- 用户可通过文字发起查询、分析、生成草稿、跨模块执行任务；根据目标识别店铺、商品、订单、时间范围，缺关键条件时询问确认。
- 支持多步任务、追问、调整目标、查看执行进度、暂停/取消/继续；允许从商品详情、订单详情或报表中直接携带业务上下文发起操作。
- 明确显示 Agent 的建议、即将实施的变更、已完成的真实操作和未能执行的动作。
- **P0 Agent 原生性：** 在同一用户目标下，按受控计划选择至少两项不同技能（如指标查询→异常任务、订单核对→客服草稿）；对工具结果作条件判断并在执行记录中可见，而不是预录一段固定聊天回答。技能选择和计划可动态，业务事实计算和写入许可必须由确定性规则控制。
- **V1.0 补充——AI 驾驶舱/收件箱：** 进入工作台时优先展示可验证的 AI 巡检摘要、异常事项、已生成的草稿、待审批事项与运行记录；允许查看 Agent 为何提出建议、为何停止和下一步需要用户做什么。P0 仅对最近一次已导入并分析的数据汇报，明示“数据截至”和“分析完成”时间；未运行分析不得制造主动发现记录。

### SO-004｜一键今日运营【P0｜Agent 原生】
- 一次启动依次检查店铺数据同步、销售变化、订单与物流状态、客服消息、库存与补货风险、Listing 质量、价格利润、营销异常，并建立待办事项。
- **默认自动执行仅限显式白名单、具有确定性校验且具备授权的内部低风险操作**（如创建待办、保存草稿、为内部任务打标签）。退款、改价、发货、广告支出、批量发布、对外发送等仍属 R2，默认需要审批；不得由 LLM 自行宣称某操作“低风险”。受控外发演示遵循第 22 节的独立门禁，不改变 R2 的默认要求。最后输出今日完成/待审/失败报告。
- 支持阶段性结果、失败继续与重新运行；不能因重复启动而重复发货、退款、发信或提交订单。
- **风险定义补充：** R1 可自动执行 = 卖家事先明确授权 + 业务工具白名单 + 数据足够新 + 确定性前置检查通过 + 本地可恢复且无不可逆外部影响；不满足任一条件即转待审或仅草稿。R2 外发不得因为通过这些条件就变为 R1，只能按单次审批或限定范围的独立预授权策略执行。
- **P0 今日运营最小切片：** 只巡检已导入且可验证的订单/订单行、商品、库存快照、消息与已知成本；广告和实时物流数据不可得时清楚标“未检查（无数据/无授权）”，不把检查列表全部标绿。

### SO-005｜主动异常发现与运营待办【P0｜Agent 原生】
- 识别销售/利润波动、库存过低或积压、履约超时、评价问题、价格失真、客服积压、同步失败、广告异常和经营数据缺口。
- 每个待办包含对象、触发依据、严重程度、建议操作、业务影响、负责人（默认卖家）、截止时间和处理状态；允许接受、忽略、延期、修改或委托 AI。
- 异常分析区分确定事实、可验证的关联和未证实的假设；提供返回源数据的路径。
- **P0 最小异常集：** 订单未履约或状态异常（有时间与状态才判断）、库存低于卖家设定的阈值（库存可用时）、已知费用下的低毛利商品、待回复消息；无库存快照不等于库存为零，缺物流更新不等于物流延误。
- **V1.0 补充——AI 收件箱操作：** 异常卡片应支持定位原始证据、查看建议与风险、转为待办、延期/忽略、进入审批；相同源数据、同一检查口径和同一异常不应在重跑后无条件产生重复未结待办。

### SO-006｜定时运营与经营通知【P1｜Agent 原生】
- 支持日报/周报/月报、定时巡店、周期性库存检查、评论监测、未发货订单追踪、规则检查和营销复盘；可启停、修改和查看运行历史。
- 业务事件可触发提醒或待办；支持汇总通知、紧急提醒和免打扰设置；在外部渠道失败时仍可在站内查看结果。

## 2. 第二中心：选品与商品运营中心

### SO-007｜多平台店铺授权与同步【P1｜外部连接】
- 添加、授权、重新授权、断开店铺；管理市场/站点、授权有效性、可读/可写能力、最近同步状态、失败原因。
- 统一筛选与查看多个店铺的商品和订单；支持人工触发增量同步；明确渠道特有字段和未开放的操作。
- 保留 Amazon、Walmart、eBay、Shopify、TikTok Shop、Newegg、Temu、SHEIN、WooCommerce、Best Buy 的候选连接需求，但以各平台实际可授权能力为准。
- **接入状态：** 每渠道/每动作分别标记“官方文档显示可支持 / 账户已获授权 / 测试店实际调用成功”。单有文档不能标为本项目已接入；MVP 无真实渠道时使用模拟和文件导入，V1.0 可优先验证 Shopify 测试店。

### SO-008｜统一商品主档与 SKU 映射【P0｜业务支撑】
- 管理 SPU、平台 Store SKU、仓库 WH SKU、产品变体、品牌、规格、尺寸、重量、原产地、采购成本、售价、素材及状态。
- 同一商品主档可关联多个店铺 Listing；商品主档、各渠道 Listing 和仓库库存各自保留独立编号/状态，支持映射维护、重复识别和历史版本。
- 商品创建、编辑、归档、上下架请求、搜索过滤、批量更新及 Excel/CSV 导入导出；对未同步成功的更改给予提示。
- **P0 最小范围：** 以 `店铺标识 + SKU` 确定单个商品，保留商品名、已知售价/币种、单位采购成本/币种、真实商品参数与可选图片；只需一对一订单行映射。完整 SPU/多变体/跨仓 SKU 映射、上下架、批量跨平台写入为长期需求，不是 P0 门槛。

### SO-009｜商品批量采集与在线素材采集【P1｜外部连接】
- 支持单商品链接、批量采集商品链接、允许的商品列表和店铺页面的商品信息采集；采集图片、价格、规格、描述和其他许可获取的字段。
- 支持浏览器插件在当前页面提取商品/图片，并导入候选商品库；提供采集预览、字段校验、去重、分类、属性缺失提示、数据清洗与来源记录。
- 不将网页商品素材自动视为可商用资产；平台不允许采集或无法合法获取的数据须停止，并提示改用授权数据或文件导入。

### SO-010｜AI 选品研究与商品机会池【P1｜Agent 原生】
- 结合关键词、目标市场、品类、价格区间、候选供应商报价、真实评论和合法获取的竞争数据进行选品筛选。
- 形成需求信号、竞争情况、价格带、成本与利润可行性、风险以及拟验证事项；收藏、比较、淘汰或移入新品上架流程。
- 对销量、市场规模等不能直接读取的数据标记“估算”，附数据来源和时间，不能作为真实销量展示。
- **置信提示：** 竞品销量、市场规模、搜索热度、热销排行的估计不可与店主真实销售数据混在同一口径；显示第三方模型/公开信息/人工上传的来源类别及覆盖时间。

### SO-011｜Amazon 专项选品工具【P2｜外部连接】
- 单独提供 Amazon 热卖商品研究、关键词研究、销量预估、类目竞品分析和 Buy Box（Featured Offer）相关因素研究。
- 展示参与 Buy Box 竞争时可获得的价格、库存、配送、账户状态等数据和可能的经营建议；不承诺获胜或保证估算精度。
- 相关商品发布检查包含 GTIN/UPC/EAN 或适用豁免、品牌、变体父子关系、站点类目必填项和政策提醒。

### SO-012｜竞品研究与持续监测【P1｜Agent 原生】
- 支持单个/多个竞品在标题、参数、卖点、图片、价格、优惠活动、评论与评价等维度的结构化对比。
- 监测有可靠数据来源的价格变化、促销变化、在售/下架和可见库存状态，保存采集时间和历史趋势；输出差异化运营建议。
- 对竞品销量、精确库存、广告支出等不可见数据不得冒充实测。

### SO-013｜VOC 客户评论洞察【P1｜Agent 原生】
- 导入或授权读取本店与竞品评价；支持语种识别、正负面分类、主题聚类、痛点/卖点总结、质量问题与使用场景提取。
- 为每个结论保留可追溯的评论样本、时间、样本数量、采样偏差说明；对反讽、混合情绪和低资源语种允许标记“无法可靠判断”，支持人工纠错；支持把发现转成商品改进、Listing 调整、客服知识或营销素材任务。

### SO-014｜商品信息质量与批量运营【P1｜业务支撑】
- 检查商品字段完整性、规格/素材一致性、属性缺失、重复 SKU、可疑描述、品牌与商品编码问题。
- 批量编辑商品、价格、库存和素材，支持草稿/审核/生效状态及失败明细；对多店铺同步冲突给出解决建议。

### SO-015｜多渠道 Listing 刊登【P1｜外部连接】
- 平台类目与属性映射、目标站点商品信息补齐、图片和变体关联、价格与币种转换、刊登草稿、预览、校验和批量提交。
- 发布状态包含草稿、待核验、待审批、提交中、平台处理中、成功、失败；查看平台返回的错误并支持修复后重试。
- 商品上下架、修改、状态回传均以实际授权的渠道能力为准。
- **写入边界：** 真实平台写入成功需获取平台确认的资源标识与状态；若仅已提交请求或队列任务，必须显示“待平台确认”。

### SO-016｜单 SKU / 批量 / 整店商品搬家【P2｜外部连接】
- 将源店铺商品映射到目标平台：单个 SKU、选择多个 SKU 或整店迁移；保持商品来源、素材来源与映射记录。
- 自动辅助类目和属性匹配、多语种转换、尺寸/单位/货币处理、重复 SKU 检测、品牌/编码风险提示、目标价格规则校验。
- 支持仅生成草稿或批准后提交；逐项显示迁移成功/失败、缺失字段和可补救操作。

### SO-017｜价格跟踪、自动调价与价格同步【P1｜Agent 原生】
- 手动单品/批量调价、竞品价格与促销监测、定时调价、基于竞品规则的调价、跨店价格同步；允许按店铺、市场和 SKU 设置不同规则。
- 设置最高/最低售价、利润底线、价格变动幅度、适用时间、规则优先级、启停及预览；提供调价前后预计利润和操作日志。
- 价格修改须核验成本、币种、数据时效、平台价格限制及授权；不能以 LLM 自由生成数字取代确定性利润校验。

## 3. 第三中心：AI 内容与营销中心

### SO-018｜AI Listing 创建、编辑与批量优化【P0｜Agent 原生】
- 支持商品资料生成 Listing、已有 Listing 优化、通过商品图片辅助生成、关键词挖掘、标题/描述/五点卖点/标签/SEO 草稿。
- 支持站点风格约束、多个候选版本、批量生成、前后差异比较、人工改写、历史版本及审批后更新商品。
- **P0 最小范围：** 依据卖家录入或导入的可核对商品事实，生成一款商品的标题/描述草稿，展示旧版/新版差异、事实校验、审批和本地版本保存；不要求批量发布、真实平台改写或图片生成。

- **V1.0 补充——变更证据：** 新旧文案对比须关联源商品事实与版本；AI 对卖点作出的事实陈述能定位到商品参数、已验证政策或卖家明确提供的资料；创意表达可标为“候选建议”，但不得伪称数据证据。

### SO-019｜多语种本地化与跨境文案规范【P1｜Agent 原生】
- 目标市场语言与表达方式适配；单位/尺寸转换，品牌、SKU、型号、技术参数和禁止翻译术语保持一致。

### SO-020｜AI 灵感图、商品图与图像编辑【P1｜Agent 原生】
- 文生图、参考图作图、AI 灵感图、广告创意图、商品场景图、商品图合成、背景替换、智能换色、相似图裂变、多种比例和风格批量生成。
- 管理原图/参考图/生成图；展示差异并检查商品外观、LOGO、尺寸、配件和其他真实属性是否被错误改变；允许卖家挑选并关联 Listing。

### SO-021｜AI 商品营销视频【P2｜Agent 原生】
- 基于商品资料、图片和卖点生成脚本、镜头内容、字幕、标题、短视频及多语言营销版本；查看生成任务进度与结果。
- 视频可预览、调整、复用素材、版本管理；针对可能虚构产品效果或误导消费者的片段给出审核提醒。

### SO-022｜统一营销素材库【P1｜业务支撑】
- 保存原始图片、采集素材、经授权的参考素材、AI 图片、视频、字幕、文案和模板；支持关键词、商品、渠道、活动关联。
- 支持版本、来源、使用授权说明、批量导出和素材复用；清楚标识生成内容与真实产品照片。

### SO-023｜品牌、促销、营销邮件与营销策划【P1｜业务支撑】
- 品牌监测、促销活动（含有能力的平台特定促销，如 eBay 促销）、活动日历、节日与地区化营销、增长策略、跨境市场策略和活动草稿。
- 包含营销邮件的受众分群、模板、文案生成、计划与发送结果、退订状态及效果统计；与订单通知/客服邮件分开管理。
- 根据商品表现、库存、受众和预算建议营销动作；支持活动版本及实际效果回顾。

### SO-024｜广告运营与效果优化【P2｜外部连接】
- 管理可获得的广告活动数据、指标、预算、创意和关键词；比较 ACOS/ROAS 等平台适用指标、分析异常、生成预算或竞价优化建议。
- 广告创建/调整仅在有真实接口及授权条件下进行，修改前提示预算消耗和风险；无接口时保留分析、建议和待执行草稿。
- **接口预评估：** Amazon Ads 等渠道公开存在广告写入 API，但通常需要申请与特定编辑权限；未通过真实账号授权前，本项目状态只能是“官方文档支持、尚未验证”，不能标为已完成投放。

### SO-025｜社交媒体内容、SEO 与 GEO【P2｜外部连接】
- 针对 TikTok、Instagram、Facebook、YouTube 等已授权账号制作多平台社交内容与发布计划，支持内容适配、评论洞察、表现跟踪。
- 为独立站提供常规搜索 SEO 与面向 AI 搜索可发现性的 GEO 建议；GEO 只能做内容结构和引用可用性检查，不能承诺特定模型收录或排名。

### SO-026｜TikTok 达人运营【P2｜外部连接】

- 批量联络限于平台允许和真实授权的范围，防止超频、重复触达或骚扰。

## 4. 第四中心：订单与客户服务中心

### SO-027｜统一多平台订单总表【P0｜业务支撑】
- 统一查看多店铺订单、状态、商品、支付/结算信息（如获授权）、买家联系字段、配送信息、时间、来源及订单异常。
- 支持多条件搜索过滤、导出、订单详情与货件/售后/财务关联；多平台状态不能简单假定完全一致。
- **P0 最小范围：** 从 CSV/Excel 还原订单及订单行，以 `店铺标识 + 订单号 + 行号 + SKU` 关联商品；保留订单时间、状态、数量、成交单价/币种，以及可选履约状态。无需实现平台订单编辑、支付流转和完整履单；跨平台订单号不得直接当全局唯一键。

### SO-028｜可配置的自动审单规则【P1｜业务支撑】
- 卖家按平台、店铺、**SoloOps 内部合法维护且可可靠关联订单的风险标签**、金额、重量、数量、国家/省市/邮编、可获得的地址异常线索等条件建立审单规则。**不假定 Amazon、eBay 等提供可直接读取的买家风险评分或任意买家身份字段。**
- 支持规则启用、停用、排序、复制、修改、测试；匹配规则的订单进入待核查，显示触发原因和人工放行/驳回动作。
- 风险标记不等同于平台封禁，也不代表可以未经核实拒绝交易。

### SO-029｜订单编辑与批量操作【P2｜外部连接】
- 支持渠道允许范围内的创建手工订单、编辑货件、合并/拆分订单、变更收件信息、取消订单及批量处理。
- 明确适用状态、影响金额及失败原因；已发货、已退款或不可修改订单不能假装更改成功。
- **客服跨订单操作：** 支持从售后对话提出修改地址、物流拦截、取消等处理草稿，但是否可以真正修改取决于订单/货件状态及渠道 API；不可操作时提供原平台操作指引，不能以生成草稿代替真实完成。

### SO-030｜AI 订单巡检与异常处理【P0｜Agent 原生】
- 主动识别订单超时、可售库存不足、缺少地址/仓库映射、重复记录、异常取消和履约状态不一致。
- 形成处理任务与操作建议；低风险已授权事项执行，涉及发货、资金、客户权益的动作交人工确认。
- **P0：** 允许将导入订单关联至本地待办、检查异常状态、附带数据来源并记录处理结果；绝不将内部标记直接写回真实平台。

### SO-031｜统一客户消息与邮件中心【P0｜业务支撑】
- 汇总平台站内信及获授权邮箱消息（如 Gmail、Outlook 等）；支持未读、待回复、优先级、标签、需要人工、无需回复标记、会话搜索。
- 消息关联客户、商品、订单、物流与售后历史；跨渠道显示当前可读/可回复能力，保留原始消息及语言。
- **P0 最小范围：** 用户手动输入或导入来自合法渠道的客服消息，记录消息来源、语言、文本、时间和经核验的关联订单（可无）；导入消息并不意味着 SoloOps 有该平台的回复权限。只有用户主动连接、验证的外发通道才可进入第 22 节受控发送试点。

### SO-032｜多语言 AI 客服与人工接管【P0｜Agent 原生】
- 支持语言检测、意图识别、情绪线索、多轮会话、客服 SOP、商品/订单/物流查询、AI 草稿、多语言回复、人工润色与发送。
- 将一条消息识别为**可并存的多个意图**（例如物流查询 + 退款请求）；只要包含退款承诺、赔偿、争议、身份不明、未知物流状态、数据过期或政策冲突，整条对外回复默认交由人工审核，并生成引用证据与对话摘要。
- **P0 默认仅生成草稿，不向真实买家自动发送。** 允许在卖家控制且已验证的测试收件箱中演示真实发送，需审查/批准或满足严格限定的测试预授权；P1 再针对符合资格的单一真实渠道开放受限自动回复。严禁将 CSV 快照误当作实时物流状态。
- 记录回复所依据的数据；不得虚构物流单号、承诺无法确认的退款或擅自泄露其他客户数据。
- **售后执行闭环：** 客服不只生成文字；可创建内部售后任务、校验订单、生成地址修改/物流拦截/退货处置方案；实际外部动作依照 SO-029、SO-035、SO-045 和审批规则执行。

### SO-033｜客服知识库完整管理【P0｜业务支撑】
- FAQ、商品手册、售后政策、物流说明、保修条款、标准话术分类；手工编辑与 Excel 批量导入、标签和专用术语维护。
- 重复知识检查、政策版本/生效时间、过期提示、问答测试、问题反馈与人工纠错；保留引用来源，缺乏依据时允许拒答。
- **P0 最小范围：** FAQ/退换货/物流规则的文本导入或录入、出处与版本标注、问答检索和拒答；完整批量运营、知识库问答评估与生命周期治理按原需求逐步增强。

### SO-034｜客服自动化规则与效能度量【P1｜Agent 原生】
- 自动分类、优先级识别、无需回复标记、草稿生成、符合条件的自动回复、关怀邮件、消息模板与多语言模板。
- 配置触发条件、白名单/排除规则、去重、发送时机；查看发送成功/失败、人工接管率、回复耗时和用户反馈。

### SO-035｜售后、退货、退款与争议【P1｜业务支撑】
- 管理退货申请、取消请求、退款申请、部分退款建议、售后原因、退货授权（RMA，若适用）、退货运单、投诉工单和争议证据。
- 支持关联订单、退款金额校验、库存与财务联动、进度追踪及人工决策；资金退款必须经授权且不得重复执行。

### SO-036｜买家档案与客户分析【P1｜业务支撑】
- 记录在授权范围内的客户资料、订单历史、会话、售后、购买偏好和客户标签，支持客户分组、复购分析及合规的营销跟进。
- 支持资料更正、导出/删除请求与联系人权限管理；不得用不可靠推断替代客户明确提供的事实。

### SO-037｜内部客户风险标签与黑名单【P1｜业务支撑】
- 提供客户黑名单页面，允许在订单或客户管理中标记风险买家、记录原因、查找/修改/解除标记，并与审单规则关联提醒。
- **明确这是 SoloOps 内部风控标记，不是对 Amazon、Shopify 等平台账号实施封禁；不能因为标记就直接阻止平台同步订单。**

### SO-038｜一键邀评、自动邀评和售后关怀【P2｜外部连接】
- 对符合平台政策的订单执行人工或规则化邀评；支持订单筛选、资格检查、时间窗口、已邀评去重、发送结果及失败原因。
- Amazon 官方 Request a Review 场景应使用其允许的标准化机制，不得伪造自定义官方邀评内容，不得诱导好评或重复发送。
- 关怀邮件、交易通知与商业营销分开管理，并遵守平台联系和客户许可规则。
- **邀评不等于自动群发：** 平台未公开且允许的发送行为只保留订单筛选、提醒、合规模板草稿和官方入口；发送去重依据订单+渠道+时间窗口。

### SO-039｜交易风险与异常行为监测【P1｜Agent 原生】
- 风控：异常金额、批量/重复下单、重复退款、地址异常；**IP 或设备等风险线索仅在合法取得且满足隐私约束时启用**，不能假定各平台订单 API 提供此类信息。产生待核对记录，不仅凭模型推测取消真实订单。
- 根据规则生成风险原因与证据摘要，支持人工核对、解除警示、错误标记反馈和后续风险统计；与 SO-028 自动审单、SO-037 内部客户标记关联。

## 5. 第五中心：供应链、仓储与物流中心

### SO-040｜自营仓、海外仓与平台仓管理【P2｜业务支撑】
- 管理自营仓、第三方海外仓与平台仓，维护仓库地址、可服务地区、时区、启停状态和出入库方式；保留 FBA、Newegg SBN、Walmart WFS、Shopify 仓储/履约服务等适用场景。
- 展示不同仓库的实际可用操作；在没有仓库授权或库存同步能力时允许记录/导入，但不得声称能直接指挥仓库发货。

### SO-041｜库存明细与库存流水【P0｜业务支撑】
- 以 SKU/仓库/渠道展示在库、可售、预留、在途、待入库等数量；记录入库、出库、退货回库、盘点、调整及损耗原因。
- 提供库存清单、库存流水、预警阈值和历史查询；处理订单、仓库、平台库存的关系，防止重复扣减和错误超卖。
- **最小库存口径：** MVP 只需导入/维护 SKU 库存快照、快照时间、库存安全阈值与基础异常；**库存模块在 P0 可选，有快照才检查，无快照标记“未知/未检查”，不报零库存。** 多仓、真实跨平台同步及复杂出入库流程由后续 SO-040、SO-042、SO-045 承担。

### SO-042｜跨平台库存同步与差异处理【P1｜外部连接】
- 支持授权同步、手动同步、同步日志、同步失败重试、数据新鲜度提示、店铺库存与仓库库存不一致检查。
- 针对同一实物库存跨平台出售的情况，提示共享库存、预留及安全库存规则；库存时间戳滞后时不得呈现为实时准确库存。

### SO-043｜AI 补货与滞销管理【P1｜Agent 原生】
- 根据历史销量、库存覆盖天数、在途库存、采购交期、物流周期、季节与促销信号提出补货建议，并标注使用的数据和预测不确定性。
- 生成需要补货的 SKU、数量范围、采购成本和预计到货建议；发现滞销/积压库存并建议促销或采购调整。

### SO-044｜供应商、工厂采购与采购单【P2｜业务支撑】
- 供应商档案、联系人、商品供应关系、历史报价、成本/币种、MOQ（最低起订量）、采购交期、采购草稿、采购确认、到货与采购退货记录。
- 报价比较、采购成本分析、异常提醒；保留“个人卖家向工厂采购”的能力，不建设供第三方工厂入驻卖货的平台经营系统。

### SO-045｜订单履约：自营仓与海外仓【P2｜外部连接】
- 指定仓库、核对 SKU/库存/目的地址、生成出库单、查看仓库接单、追踪拣货打包、出库和物流状态，并在平台允许时回传追踪号。
- 支持订单异常与重复出库校验；实际出库、渠道回传及商品库存状态保持一致。

### SO-046｜平台仓的跨渠道多渠道履单【P2｜外部连接】
- 支持使用具备条件的平台仓库存履行其他渠道订单的业务方案：Amazon MCF、Newegg SBN 多渠道、Walmart WFS 等（实际支持以授权为准）。
- 流程包括仓库授权/启用、主档 SKU—渠道 SKU—仓库 SKU 映射、选择履单仓、提交多渠道履单、跟踪处理状态和物流单号回传。
- 提醒渠道服务条款、包装、物流承运方式、费用和绩效限制；不能把未真实创建的出库单写成“已发货”。
- **接口预评估：** Amazon MCF 官方存在履约创建接口，但需要符合条件的卖家、角色和数据授权；其他平台仓的多渠道履单不能据此类推为均可使用。

### SO-047｜物流商、地址与打印配置【P2｜业务支撑】
- 维护物流商、物流服务、尾程渠道、海外仓配送关系、发件/退货地址簿、包裹规格模板、打印设置、面单模板和报关模板。
- 可查看各物流渠道的覆盖国家、限制条件和费用信息来源；支持包裹打印配置校验与操作记录。

### SO-048｜自动物流分配与购买面单规则【P2｜外部连接】
- 支持创建、排序、停用和测试物流规则；按渠道、店铺、目的国/州/邮编、SKU、重量、体积、数量、金额、仓库库存等条件设置优先级规则；提供就近仓库候选及适用物流渠道推荐。
- 支持仅自动分仓、自动生成面单购买草稿、经授权自动购面单、打印和异常处理；提供规则预览、启停、优先级和执行历史。
- 不满足仓库库存、尺寸限制、配送限制及收费权限时不能直接购面单或标记已发货。

### SO-049｜头程物流询价与货件管理【P2｜外部连接】
- 管理头程询价、运输方案对比、报价币种/有效期、发货单、货件、包裹、承运商、预计时效和费用记录。
- 支持订单/货件批量编辑、运单打印、物流轨迹查询、超时预警及跟进记录；若无实时报价接口须标明为手工维护价格或历史参考价。

### SO-050｜跨境申报与品类合规资料辅助【P2｜业务支撑】
- 管理商品原产地、申报品名、材质、估价、HS 编码候选、品牌授权/资质文件（如有）、目的市场所需申报字段和报关模板。
- 提示缺失的申报/合规资料、特定商品市场限制及需要人工核验的项目；只做资料整理和风险提示，不伪称已完成海关、税务或平台认证审核。

### SO-051｜仓储与供应链优化【P2｜Agent 原生】
- 对比库存分布、仓储费、跨仓调拨、头尾程成本、补货周期与售罄风险，输出库存布置及采购/物流优化建议。
- 针对订单履约与采购需求产生可执行任务草稿，记录假设、约束和卖家最终选择。

## 6. 第六中心：财务与经营分析中心

### SO-052｜销售、订单和经营报表【P0｜业务支撑】
- 统计店铺/渠道/市场/商品维度的销售额、订单量、数量、退款、退货、客单价、销量排行、时间趋势，并支持筛选、比较、导出。
- 提供日报、周报、月报和自定义区间，指标需有明确口径、币种、订单状态和数据完整度。
- **P0 最小范围：** 对导入且状态可确定的订单行做单店铺、单币种、指定时间窗口的销售数量/销售额聚合；后续再扩展多店铺、多币种和结算对账。

### SO-053｜实际成本与商品/店铺利润【P0｜业务支撑】
- 归集采购、头程、尾程、包装、仓储、平台佣金/服务费、广告、折扣、退款、退货损失及其他费用；支持 SKU、订单、店铺和市场层面的利润展示。
- 明确“销售毛利”“经营净收益估算”“已结算利润”等口径区别，并区分已确定、待入账、分摊及估算成本。
- **数据不足时的行为：** 费用缺失或未结算时不得给出虚假的“精确净利润”；允许只给已知收入、已知费用及基于假设的区间。
- **P0 最小范围：** 以订单行销售额、数量与已导入的单位采购成本计算有凭据的“已知毛利/毛利估算”，非采购成本类费用缺失则标记未计入。利润无法归属具体 SKU 或跨币种缺汇率时，不作精确排行。

### SO-054｜独立新品利润计算器【P0｜业务支撑】
- 不依赖真实订单即可输入候选售价、采购价、头尾程、平台费用、仓储、广告、退款/税费假设、结算币种来估算单件利润、利润率和保本售价。
- 比较多个售价/物流方案及敏感性变化，给出合理的最低价建议；醒目提示假设项、缺失费用及估算性质。
- **确定性规则：** 货币换算、佣金、成本与保本价由计算规则得到，AI 不得直接臆造计算结果；每个假设可追溯。
- **P0 最小范围：** 单件商品自填售价、采购价与明确提供的费用项，能计算已知单件毛利及情景分析；缺物流/平台费必须明确警示，不输出真实净利润承诺。

**V1.0 P0 利润可信度补充（SO-053、SO-054）：** 已知毛利、贡献利润、净利润是不同统计口径；缺物流、广告、平台佣金或税费时不得显示“已确定净利润”。每个可计算金额必须明确币种、订单状态、费用归属及数据来源，支持用户展开公式、关联订单行和已知成本记录；价格建议不得由大模型凭空给出单独数字。
### SO-055｜渠道账单、结算与回款【P1｜业务支撑】
- 导入或同步平台交易与结算账单、销售款、退款、平台扣费、提现/回款及结算周期；按店铺/平台和时间追踪账单状态。
- 提供原始账单明细、结算汇总、尚未到账和已核对状态；不把未到账金额当作已收现金。

### SO-056｜平台费用映射、自定义费用与对账差异【P1｜业务支撑】
- 将 Amazon、Newegg 等平台原始收费项映射为统一成本类别；支持卖家自定义费用、类别归属、分摊方式及规则调整历史。
- 检查订单金额、平台账单、物流费和退款项之间的差异，生成待核实清单；不自行改写平台原始记录。

### SO-057｜AI 自然语言经营问数和异常解释【P0｜Agent 原生】
- 支持“哪些 SKU 销量高但不挣钱”“哪个渠道物流成本异常”等问答；**先检查跨来源 SKU、订单、费用映射和时间区间是否完整**。具备足够数据时给出确定性指标计算及所用口径、筛选条件、来源明细；费用或物流字段缺失时仅回答可以验证的部分，并明确拒绝给出虚假的精确利润结论。
- 分析销售、利润、库存、退款及广告数据变动，区分证实的影响因素与假设；可以从分析直接创建优化任务。
- **P0 必须实现的自然语言问数：** 对限定的问题意图（销量排行、收入对比、已知毛利排行、“销量高但已知毛利低”等）执行受控、只读的确定性统计，展示筛选范围、口径、来源和缺失字段；**不允许 Agent 自行拼接可执行的任意 SQL 或跨无关店铺查询。** 不可答的问题给出需要哪些字段。

**V1.0 P0 经营问数溯源要求（SO-057）：** 由受控查询/统计工具执行数据筛选和金额计算，LLM 仅解释结果、组织后续建议。返回数值型断言时提供计算口径、时间范围、订单/费用行引用、排除项、汇率来源；在证据不足时回答“无法确定”并列出需补的数据。固定统计口径的重复查询应产生相同数值，不要求自然语言措辞逐字一致。
### SO-058｜运营变更版本、A/B 测试与效果评估【P2｜Agent 原生】
- 跟踪 Listing、价格、广告和营销内容的版本与生效时间；比较前后指标，并说明市场与外部因素可能带来的干扰。
- 在满足条件的渠道支持受控 A/B 试验与结果记录；没有可靠实验设计时不能宣称 AI 导致特定销量增长。

### SO-059｜多币种、汇率、税费与数据完整性【P1｜业务支撑】
- 允许录入交易原币、核算本位币、适用汇率及日期；显示费用归集和指标是否完成同步、哪些字段未知。
- 支持店铺/市场相关税费、VAT/GST、关税及申报相关信息的记录与估算提醒；不代替专业税务申报或自动作合规结论。

## 7. 第七中心：AI 自动化与扩展中心

### SO-060｜内置运营 Skills【P0｜Agent 原生】
- 将商品采集、选品、竞品、VOC、Listing、AI 图像/视频、刊登、调价、订单、客服、库存、补货、采购、物流、财务、营销、达人、风控封装为独立可调用技能。
- 每项技能显示功能说明、所需数据、授权权限、可产生的变更、适用范围和运行结果；支持独立使用及组合成一键任务。
- **P0 范围：** 固定、受控的“数据检查、指标/利润问数、异常建待办、客服草稿、Listing 草稿”技能即可，不要求开放式技能市场。每个内置技能**必须声明名称/用途、输入字段与来源、输出结构、读取范围、可写范围、R0–R3 风险类别、执行前置条件、可能副作用、去重标识和确认结果方式**；不能直接运行技能附带的任意代码。

**V1.0 P0 内置 Skill 元数据要求（SO-060）：** 每项技能最少声明唯一名称与版本、用途、必填输入及类型、输出结构、所需用户/店铺权限、允许调用的业务工具、R0—R3 风险等级、是否产生副作用、幂等/重试限制及失败处理。未声明或校验失败的技能不能执行。LLM 不得自行提高风险等级对应的权限。
### SO-061｜第三方 Skills 安装与生命周期管理【P2｜外部连接】
- 允许用户查看、导入、安装、启用、升级、禁用和卸载通过审核的第三方 Skills（包括许可证允许的开源 Skills）；展示来源、版本、发布者、声明的工具权限、网络访问范围与更新差异；默认不允许执行任意不可信代码。
- 第三方 Skills 必须经过来源/许可证核验、权限清单和版本审核；仅允许通过受控业务工具调用，凭据不透传到技能文本，敏感写入需再次审批。涉及可执行代码的扩展需要隔离环境、资源限制和审计，**在落实隔离以前不开放安装执行**；升级可能新增权限时必须重新确认。

### SO-062｜可配置运营工作流【P0｜Agent 原生】
- 支持定时、手工与业务事件触发；多步任务、条件分支、异常节点、人工确认、暂停继续、失败处理和任务模板。
- 例如库存不足→生成补货方案→卖家审批→创建采购草稿；评价问题上升→分析评论→生成 Listing 修改建议→人工审核。
- 支持工作流启停、复制、条件修改和执行记录，避免因重复事件重复触发有副作用的操作。
- **P0 范围：** 提供最小流程执行语义：`触发→调用受控技能→条件分支→（可选）审批→执行/保存→结果核验→结束`；支持节点输入输出、暂停/恢复、重复运行去重、失败状态。流程模板可固定且以声明形式管理，**不要求拖拽编辑器、任意脚本执行或通用流程平台**；但必须能看到 Agent 根据中间结果选择了哪项技能和分支。

**V1.0 P0 工作流约束补充（SO-062）：** 固定业务模板亦需支持技能节点、确定性分支、人工审批节点、结束/失败/人工接管节点，并能够记录节点输出与下一步选择。可动态选择白名单技能，但不建设通用拖拽引擎、任意脚本执行器或复杂框架，只要求可观察、可暂停、可恢复。
### SO-063｜跨平台连接器中心【P1｜外部连接】
- 管理电商、仓储、物流、广告、客服邮箱、独立站、社媒及经授权的第三方数据源；显示可读取/可写入功能、授权期限、失效及重新连接状态。
- 支持连接测试、断开授权、同步结果与调用异常可见；未获得权限时允许导入文件或模拟验证，但必须标清能力状态。

### SO-064｜浏览器扩展/页面内 AI 助手【P2｜外部连接】
- 面向允许使用的网页提供批量商品采集、在线图片采集、评论洞察、竞品比较、当前商品 Listing 优化、TikTok 达人协助、邮件/站内信 AI 客服草稿。
- 扩展可把采集数据或任务提交到主运营中心，查看回执和进度；遵守平台访问、版权、采集及营销限制。

### SO-065｜软件使用助手与新手引导【P1｜业务支撑】
- 使用产品帮助文档回答平台操作问题；按当前模块提供简洁教程、功能使用样例、错误解释和任务引导。
- 区分“解释如何操作”和“已经代为操作”，不在没有用户授权时自动修改业务数据。

### SO-066｜经营规则、偏好与可验证的业务记忆【P0｜业务支撑】
- 记录目标站点、常用仓库、物流偏好、品牌语言规范、客服话术、利润底线、广告预算、风险阈值及允许的自动执行范围。
- 卖家可查看、修改、撤销和重置偏好；重要经营约束须明确生效条件，不因对话模型遗忘而失效。

### SO-067｜审批、操作前预览与回退边界【P0｜Agent 原生】
- 将“只读查询”“生成草稿”“低风险已授权执行”“高风险待审批”区分处理，提供操作对象、旧值/新值、预计费用、风险和影响范围预览。
- 支持单条和可安全分组的批量批准/拒绝；对价格、退款、发货、批量上架、广告预算和客户联系等执行完整权限检查。
- 对能够撤销的修改保留原始值与恢复操作；对真实退款、外部邮件、发货等不可可靠回退的动作提前说明，不假称“全部可撤销”。
- **P0 外发特别规则：** 不把邮件发送降为 R1。仅能对卖家控制且已验证的测试收件人执行受控外发，先展示目的地址、全文、关联任务、发送次数限制和不可撤销提示；真实买家自动发送遵守第 22 节先决条件和 P1 范围。
- **风险分级：** R0 只读、R1 内部可逆写入、R2 对外/资金相关敏感操作、R3 禁止或无权操作。退款/发货/改价/群发/广告支出不因金额小自动归为 R1；R3 不能靠人工点击批准来越权。

**V1.0 审批细化（SO-067）：** 每一项操作清楚展示影响对象（店铺/SKU/订单/收件人）、旧值与新值、AI 依据、风险级别、可能的外部副作用、撤销可能性及执行渠道状态。用户可单独批准、拒绝、修改；批量审批须逐项运行相同权限校验且不得绕过 R2/R3 门禁。
### SO-068｜任务状态、执行记录和异常恢复【P0｜Agent 原生】
- 记录任务开始、每一步读取/分析/草稿/审批/写入、平台响应、最终成功/部分成功/失败及用户后续处理。
- 支持暂停、继续、取消、超时提醒、失败重试、人工接管；重试先核对外部操作状态，不重复扣款、退款、发货、发信或更新同一业务版本。
- **不确定态：** 外部 API 超时或连接断开时，任务应标记“结果未确认”，先查询平台状态再决定是否重试；不可将网络超时直接当作操作失败。
- **P0 验收记录：** 每个任务至少能展示所用导入批次、技能调用、规则结果、用户审批、内部变更的实际记录；受控外发还需有通道回执以及目标测试邮箱的收件证据，不能仅凭本地“已发送”状态认定对方已收到。

**V1.0 任务熔断和人工升级（SO-068）：** 遇 R3 禁止、权限不足、违反确定性业务约束时立即停止该动作，不重试；缺关键数据则暂停并请求补充；可证实无副作用的临时网络错误允许有上限的重试（默认最多 3 次），超限转人工；外部写入结果未知不得盲目重试，先回查确认。每个多步任务另应设置总执行步数、持续时间与模型调用成本预算，超过预算需暂停，保存已完成状态并可由用户继续。不得通过更换工具或改写参数试图绕开相同阻断条件。
### SO-069｜授权的开发者 OpenAPI【P2｜外部连接】
- 为卖家自己使用的外部脚本或自动化工具提供受控调用入口，可查询获准的商品、订单、库存、任务和报表，并在授权范围内发起受限制的业务操作。
- 提供访问凭据管理、功能授权、调用记录、撤销和限额；不是面向第三方运营商提供任意越权访问。

### SO-070｜移动端轻量运营能力【P2｜外部连接】
- 在手机上查看当日销售与利润摘要、订单状态、库存预警、客服待办、AI 任务执行结果和通知。
- 对高风险任务查看变更详情并批准或拒绝；移动端强调日常监督与审批，不要求复制全部桌面工作功能。

### SO-071｜外部经营数据与提醒渠道【P2｜外部连接】
- 在取得授权的情况下连接 Google Analytics、站点流量/转化数据、邮件及第三方营销渠道；用于运营异常、漏斗分析和营销效果评估。
- 支持通过授权的邮件、飞书、Slack、Discord 等渠道发送摘要/预警/审批提醒，并保留站内通知和触达失败记录。

### SO-072｜独立站买家智能导购扩展【P2｜外部连接】
- 将商品问答、对比推荐、库存状态、自然语言购物建议和引导至商品详情/结账等能力提供给拥有前端控制权的独立站。
- 尊重用户画像与行为数据授权，支持人工接管；不在 Amazon、eBay 等第三方不可控制页面强行部署。
- **买家侧定位：** 仅支持可控制的独立站前端，在获得必要同意时利用商品属性和可用行为信号推荐；结账引导应交回官方结账流程，不能绕过平台支付及个人信息规则。

### SO-073｜独立站内容维护与基础建站辅助【P2｜外部连接】
- 提供既有店铺内容维护技能；为已拥有的 Shopify、WooCommerce 等店铺提供商品集合、首页/活动页文案、店铺说明、SEO 页面内容与部分商店配置的草稿及授权更新。
- **不建设完整的独立站建站平台/主机/CDN/商城交易系统**，理由详见“调整说明”；在卖家运营范围内保留可用的商店内容维护技能。
- **范围澄清：** 只协助已有店铺管理少量运营内容和创建草稿，不承担独立站建站器、支付、主题引擎或任意后台配置代理；只有官方接口提供对应写入权限时才做更新。

### SO-074｜账号、基础权限、系统设置与隐私管理【P0｜业务支撑】
- 个人账号、登录与恢复、店铺授权管理、可选协作者权限、操作记录、个人资料和通知设置；提供资料导出、授权撤回、删除申请等可用管理动作。
- 外部平台数据、订单地址、客户联系方式、供应商资料和经营报表需按可授权范围查看/使用；业务数据不得跨无关店铺混用。
- 保留必要的基础设置和帮助反馈入口，但不以复杂集团组织、分销商结算或租户计费为个人卖家默认业务。
- **P0 个人数据保护：** 导入订单/邮箱/客户消息时尽量只保存必要字段，隐藏不需要的完整地址和联系方式；卖家可以删除导入批次及其派生草稿/任务，审计记录保留范围应受明确政策约束。

**V1.0 用户数据保护补充（SO-074）：** 文件导入前告知使用目的；上传文件不执行其中的宏/脚本；客户个人信息不进入无关 LLM 请求；敏感凭据不写入日志、源码和测试样本；允许用户识别、撤销和清理导入批次以及相关派生结果，必要审计留存范围和期限另行说明。

## 9. 跨功能业务约束（所有模块都必须满足）

1. **真实/模拟/导入三种数据身份清晰：** 业务来源、最新同步时间、币种、估算与真实指标不能混淆。
2. **商家操作不等于自动获授权：** 店铺、站点、市场、资源、可读/可写权限以真实连接能力为准；关键写入需满足卖家同意及对应政策。
3. **业务规则不能被自然语言绕过：** SKU、订单状态、采购与库存数量、价格下限、广告限额、退款条件、平台政策等由业务规则验证。
4. **重要操作有审批、审计、不可逆提示：** 退款、批量改价、发货、批量邀请、广告预算与商品发布必须有风险边界。
5. **保证失败结果可见：** 区分成功、部分成功、等待平台确认、失败及待人工处理；无权调用时明确说明，不制造成功假象。
6. **允许人工完整接管：** AI 不可用时，核心商品、订单、库存、采购、客服、报表仍支持人工查看和处理。
7. **异步操作不重复执行：** 任务重放需核对平台状态；尤其避免重复退款、出库、邀评、面单购买、广告投放或邮件发送。
8. **售后及客户数据安全：** 只处理必要且已授权的数据；支持客户资料、邮箱和地址的保密展示及访问范围约束。
9. **内容真实性与版权边界：** 采集素材、AI 图片、视频、评论和竞品数据需保留来源及使用条件；不可宣传未经确认的商品性能或认证。
10. **跨境口径明确：** 涉及国家、语言、货币、汇率日、时区、税费、运输、市场限制和售后政策时，不能沿用单市场假设。
11. **AI 给出事实依据：** 营销预测、竞品分析、异常归因、财务结论必须显示可验证来源、计算口径或“不确定”；不承诺 AI 准确率、提效倍数和销量增长。
12. **第三方服务不可用时优雅降级：** 无合法采集方式、接口不可用、模型服务不可用、物流报价缺失等情况，保留手动维护、草稿和待办，不直接剔除需求。

| 任意网站数据抓取、素材复制、无限制达人大规模群发 | **保留 SO-009、SO-026、SO-064 的合规操作能力；不支持绕过限制** | 涉及平台访问规则、版权、隐私与垃圾营销风险。 |
| 不限额度自动退款/发货/改价/买面单/广告花费 | **保留操作能力；强制业务规则、权限和必要审批** | 资金、履约和账户风险由卖家承担，无法无约束自动执行。 |
| 第三方电商平台不可控制的买家页面嵌入导购 | **仅限独立站或已授权的买家前端 SO-072** | 个人卖家不能修改 Amazon 等平台受控页面。 |
| 一切 AI 执行均可自动回滚 | **只对确实可恢复的变更提供回退；其他操作明确不可逆 SO-067** | 发信、发货、真实退款和某些外部投放不可保证撤销。 |

## 14. P0 MVP：四条可验收子闭环与长期 E2E 对应

P0 是**可验收的真实本地业务过程**，不是“自动开通 Amazon/Shopify API”；以用户导出的 CSV/Excel 为正式数据入口，模型对多步任务进行受控组织，确定性程序负责业务计算，所有结果可追溯。**缺哪些数据就跳过哪类检查**；不能把“商品分析成功”误报为“订单同步成功”。

| MVP | 与七条长期 E2E 对应 | P0 的最小动作与预期结果 | 不在 P0 的动作 | 通过条件 |
|---|---|---|---|---|
| **MVP-01 今日运营** | **E2E-02 的 P0 子集**；可为 E2E-05 产生库存待办 | 从导入的商品/订单行/可选库存/消息/已知成本中读取数据 → 分支选择异常检查技能 → 形成有证据的待办/内部标签 → 进行审批 → 落盘并复盘 | 真实平台订单同步、自动发货、完整采购、广告、自动调价、退款 | 统计和异常可回溯到导入行；至少一个内部任务真实写入；重复运行不产生重复待办；无数据的检查标“未检查” |
| **MVP-02 AI Listing 优化** | **E2E-03 的 P0 子集**；为 E2E-01 提供内容草稿 | 读取经核对的商品事实 → 自动生成一条 Listing 候选 → 规则检查 → 前后对比 → 审批 → 本地保存生效版本 | 完整选品、图片/视频生成、类目映射、真实平台刊登 | 事实不虚构；审批前不改历史版；本地版本记录可见；不能写成已发布到平台 |
| **MVP-03 客服处理** | **E2E-04 的 P0 子集** | 手工输入/导入消息 → 多意图识别 → 核验订单/政策证据 → 生成回复草稿及人工接管摘要 → 记录处理状态 | 任意平台站内信发送、退款/改地址/物流拦截的自动执行 | 对混合退款诉求不自动发信；未知物流拒绝承诺；草稿可修改和存档；经验证的自有测试通道可按第 22 节演示真实外发 |
| **MVP-04 利润经营问数** | **E2E-02 的分析子集**；为 E2E-03/05/07 提供价格与成本信息 | 对导入订单行、SKU 采购成本和卖家给定的费用口径进行只读统计 → 回答“哪些商品销量高但已知毛利低” → 显示来源与缺失项 → 转为待办 | 真实平台利润结算、完整税务/多渠道费用归集、精确净利润承诺 | 同样输入重复计算一致；缺单位成本或币种不一致就不得精确排名；结论能查看原始行 |

**执行价值的两级验收：**

- **P0-Core（必过）：** 四条 MVP 均能操作真实的本地业务记录，并表现出“模型理解目标→选择受控技能→读取结果→根据结果采取不同动作→保存/审批→检查状态”的完整链路。不能只展示模拟聊天文字。
- **P0-External（产品宣称“具备真实外发操作”前必须过）：** 使用卖家本人控制的发送账号和测试收件箱，对一条事先认可的客服回复或经营日报执行一次真正外发，展示真实提交回执，并用收件箱实际收件佐证；按 R2 审批/授权执行。若尚未取得可用外发账号，此子验收可标“阻塞”，但不得宣称已验证真实发送，更不能给真实买家自动群发。

**前置条件：** P0 共涉及 **23 个模块**：`SO-001/002/003/004/005/008/018/027/030/031/032/033/041/052/053/054/057/060/062/066/067/068/074`。每个仅要求支持四条 MVP 的最小子能力。**SO-041 库存快照是条件数据，缺失不阻断利润、Listing、客服三项；SO-031 客服消息缺失也不能阻断利润分析。** 完整所需字段和导入失败处理见第 21 节。

**P0 不通过的情况：** 只回复“已执行”但没有业务记录；计算口径不可验证；基于缺失数据自称全店巡检通过；重复运行导致任务重复或敏感外发重复；未获授权却标记平台已修改；未经用户确认发送真人客户消息。

**进入 P1 后的强验证目标：** 优先选择一个有合法账户和相应权限的电商平台（建议先核对 Shopify 是否适用），打通“读取一件商品→生成改动→审批→调用官方 API→回读验证变化”。官方接口存在不等于项目已完成，见第 17 节。

## 15. AI 与业务操作的安全边界

### 15.1 操作等级，不由模型自由决定

| 等级 | 业务动作 | 是否允许自动执行 | 处理原则 |
|---|---|---|---|
| R0 只读/分析 | 查询订单、读取商品、生成报表、生成未提交建议 | 可在授权的数据范围内 | 清晰标注来源、更新时间与数据完整度 |
| R1 内部低风险写入 | 创建内部待办、保存草稿、内部标记、更新可恢复的工作流状态 | 可以，但**必须符合预设白名单及可恢复条件** | 业务规则确认、不跨店铺、去重、完整审计 |
| R2 对外或经济敏感 | 包括单次/批量外发消息、商品发布/改价、发货、取消订单、购买面单、退款、广告预算、达人邀约 | **默认逐次审核；仅经明示的有限范围预授权且具备前置条件时允许特定低风险对外消息自动执行** | 即使金额小也不自动降级为 R1；必须限对象/模板/频率/时效/权限、可撤销授权、确认外部结果。涉及资金/履约不得靠“发信白名单”绕过审批 |
| R3 禁止或无权 | 未获授权的接口调用、违反平台政策的采集/群发、访问其他店铺/客户敏感数据、第三方技能越权 | **不允许** | 即使用户在审批页点击同意，也不能突破平台授权与禁止规则 |

**“低风险”不意味着“AI 认为没问题”。** R1 仅包含受控的可恢复本地副作用；R2 始终保留不可逆属性，允许的有限预授权是独立门禁而非风险降级。外部平台写入默认审批，不得先自动化再补权限。

### 15.2 自动化的统一状态

`待读取 → 数据已准备 → 分析中 → 草稿已产生 → 等待审批（如需要） → 提交执行 → 待外部确认 → 成功/部分成功/失败/结果未知 → 已归档`。

外部 API 超时或断开网络属于**结果未知**，必须查询实际业务状态后才能再次写入。用户拒绝审批应结束该变更任务，但不应抹除此前的分析与草稿。

### 15.3 客服多意图、部分自动化

- 一条消息可能同时包含物流查询、修改地址、退款要求和负面情绪。需要保留**多标签意图**，而不是强制选一个“主意图”。
- 凡包含退款承诺、赔偿金额、争议、法律威胁、物流拦截或其他敏感任务，对外回复进入人工审核；可以自动准备订单事实、政策引用和多语言草稿。
- 经官方接口确证且有相应权限时，Agent 可在审批后执行被允许的地址修改、订单取消、物流拦截等业务动作；否则只保留草稿和官方操作路径，不把“客服回复了”冒充“业务已处理”。
- 面向**真实客户**的常规 FAQ/物流进度自动回复属于 P1 的可选授权功能；P0 除默认生成草稿外，只支持按第 22 节在卖家自有测试邮箱完成受控真实外发验证。

### 15.4 第三方 Skills 的额外限制

- **P0 不提供任意第三方技能安装执行**，只提供内置受控技能。
- P2 的技能接入需要身份与来源审核、版本及许可证检查、显式权限清单、工具白名单、敏感数据隔离、凭据保护、变更审计和升级后权限复核。
- 未经隔离的可执行代码、未审查的第三方脚本和任意网络访问不得被当作普通 Skill 安装。用户确认不能代替系统权限隔离。

## 16. 数据可信度与 AI 能力边界

| 数据/判断 | 必须向卖家说明 | 在什么情况下停止给确定结论 |
|---|---|---|
| 店铺订单与销售 | 店铺/日期/站点/订单状态/最近同步时间，API 还是文件导入 | 缺少时间区间或关键订单状态；同步失败导致口径不确定 |
| 商品/仓库库存 | 可售、预留、在途、快照时间；是否为共享库存 | 多渠道实时库存不明，无法保证可售数量 |
| 竞品销量/市场规模 | 是否第三方估算、公开排名信号、采样区间及供应商说明 | 无可靠源却需要“精确销量/市场份额”时 |
| 评论情感与 VOC | 样本量、语种、选择偏差、代表性原始评论及无法判断项 | 反讽、混合情绪、样本过少或被选择性采样 |
| 利润与经营问数 | 收入、折扣、佣金、采购、头尾程、广告、退款、税费、币种/汇率、结算状态 | 数据源不能关联 SKU/订单；关键费用缺失却要求“精确净利润” |
| 物流报价与送达时间 | 手工维护/实时 API/历史数据，时间与渠道限制 | 报价过期、缺承运商确认、交付时间不可验证 |
| AI 图片/视频/商品宣传 | 生成素材标识、商品实物事实来源、许可证/品牌授权 | 模型改变真实产品结构或虚构认证、性能、配件 |
| 风险标记/异常订单 | 内部规则来源、证据、允许获取的订单字段；假阳性和人工复核 | 无权获得买家身份或 IP 数据，无法支持具体风险断言 |

**数据来源分类：** A 官方授权平台数据；B 卖家主动导入的真实文件；C 获得许可的第三方数据；D 公开且允许使用的观察值；E 第三方或模型估算；F 合成测试数据。所有报表和 Agent 结论应保留可追踪来源，并明确资料时效、覆盖范围与不足。**B 只是用户导入的文件，不表示全部信息已核验，更不表示实时。**

**特别要求：** 不能因 LLM 能解释趋势就把它当统计引擎；汇率、成本、费用、利润、税费等数值必须由可核验的业务口径计算。没有数据就诚实地说“无法确定”，可改为列出需要补充的文件和字段。

## 19. 个人卖家范围调整理由（继承 V0.2，不因 P2 而删除）

- **剔除“面向其他商家的 SaaS 经营体系”**：不提供多租户收费、商家招商和复杂租户账单。理由：当前用户经营自己的跨境店，不经营“向其他卖家收费的服务商”。卖家自己的交易结算、费用和利润必须保留 SO-052—059。
- **剔除“供应商侧平台运营门户”**：不为工厂做入驻招商与结算平台；**保留**供应商报价、采购、到货、退货和供应链优化 SO-044、SO-051，因为这是个人卖家日常采购工作。
- **不重造完整 ERP**：SO-040—051 的仓配业务需求仍然保留，但应优先使用平台或既有 ERP/仓库能力，只有 Agent 需要且接口无法提供时才维护最小本地业务记录。理由：避免基础设施投入掩盖 Agent 核心价值。
- **不开发完整独立站建站/支付平台**：保留已有店铺内容维护 SO-073 与授权的买家导购 SO-072；不另造主题系统、支付和托管服务。理由：用户需要运营，非创建新电商基础平台。
- **不自动执行无权或违规动作**：原有采集、达人、邀评、广告、退款、物流功能仍在全集中，但绕过平台访问规则、越权写入、无限量群发和不可核验的资金操作不能成为功能承诺。

## 20. V0.4 评审与优先级决策记录（保留历史决策）

### 20.1 已采纳的外部建议

1. **彻底明确数据入口：** P0 允许卖家直接上传 CSV/Excel，完成商品、订单、已知成本、客服和库存分析，不要求提前拥有平台开发者资格。

5. **SO-057 明确升为 P0：** 自然语言经营问数是 MVP-04 必备，但必须受控且计算可验证。
6. **真实平台授权纳入明确阻塞条件：** P1 才检验真实 Shopify/Amazon/TikTok 等渠道读写；获批、已调用、已回读属于不同证据。

### 20.2 未照单全收的意见及理由

| 外部建议 | V0.4 处理 | 原因 |
|---|---|---|
| P0 自动回复真实买家的纯物流咨询 | **不作为 P0 无条件功能，转 P1 条件开放**；P0 提供客户草稿及卖家自有测试邮箱真实外发验证 | CSV 物流快照可能过期；客服还涉及个人信息、混合退款意图、订单匹配和平台消息权限。仅用一条“纯物流”分类结果不足以安全地执行真实客户外发。 |

## 21. P0 文件导入与最低业务数据契约（功能需求，不是数据库设计）

### 21.1 数据入口、能力分级和首次使用

- **P0 正式入口：** 用户自行导出的 CSV/Excel、手工录入、合成测试样本。用户可先导入一类数据完成可行的工作，再逐步补齐其他数据；不强制连接电商店铺、ERP 或物流供应商。
- **导入时告知：** “当前为文件分析模式：数据截至您导出的时间；可做报表、分析、草稿和本地待办，不会自动读取实时店铺状态或修改电商平台。”
- **导入批次：** 保存源文件名/来源渠道/所属店铺/导出时间（如可得）/导入时间/覆盖区间/币种/导入成功与失败行数；支持预览、错行纠正、重复导入对比、清除指定批次及其派生结果处理。
- **数据身份：** 卖家提供的真实文件属于“用户导入数据”，不等于平台当前值；合成数据一律标记“测试”。平台授权前不显示“实时同步完成”。
- **最小使用体验：** 只有商品资料也能做 Listing 草稿；有商品+订单行可做销售与已知成本分析；有客服消息+规则可做客服分类/草稿；有库存快照再做库存异常；无数据的模块显示“未检查”，不能标为“正常”。

### 21.2 P0 导入文件与最小字段

下面的字段是**业务所需信息**，不是要求建立同名数据库表，也不强求所有文件在首次使用时同时提供。

| 数据组 | MVP 真正需要的业务字段 | 主要支持 | 缺失后的处理 |
|---|---|---|---|
| **商品资料** | 店铺标识、SKU、商品名、可核对商品参数、销售价格及币种、单位采购成本及币种（若有） | MVP-02、MVP-04 | 没有商品事实不得自行补造材质/尺寸；缺单位成本不做 SKU 毛利判断 |
| **订单与订单行** | 店铺标识、订单号、订单行号/可确定的明细标识、SKU、购买数量、成交单价及币种、订单时间、订单状态；有则记录折扣、退款及履约状态 | MVP-01、MVP-04 | 缺行明细不能可靠算 SKU 销量；缺状态不得随意把下单量算为已支付销售；重复行须识别 |
| **库存快照（可选）** | 店铺标识、SKU、已知可售数量、快照时间、卖家自设安全阈值 | MVP-01 的库存巡检 | 缺失时只显示“库存未知/未检查”，不得推断缺货或现货 |
| **客户消息（可选）** | 来源渠道、消息标识（或可靠替代）、消息时间、消息正文、语言（可识别）、关联订单号（如核验）、可选发送者信息 | MVP-03 | 没有订单匹配时只生成一般解释草稿；敏感询问和物流事实不能擅自回答或外发 |
| **客服政策（可选）** | 政策文本/FAQ、适用市场或渠道、生效日期、来源、版本 | MVP-03 | 缺可信政策仅提供人工核实建议，不作退款/保修承诺 |
| **订单相关费用（可选）** | 店铺/订单/订单行/SKU 的关联信息、费用类别、金额、币种、费用发生日期 | MVP-04 的更完整利润判断 | 缺平台佣金、广告、头尾程等时只计算“已知毛利”，不称精确净利润 |
| **运单信息（可选）** | 可验证订单关联、物流单号/轨迹、承运商、状态及**最后更新时间** | MVP-03 的物流咨询草稿 | 未导入或已过时不能生成“当前物流已到达”等未经确认的结论 |

### 21.3 必须检查的导入规则

- **主键与去重：** 商品至少使用“店铺+SKU”区分；订单使用“店铺+订单号”；订单行使用“店铺+订单号+行号/可辨明的明细标识”。不同平台/店铺可能有相同订单号，不能互相覆盖。
- **订单行有效性：** 数量、成交金额、折扣和退款的正负号应符合明确的报表口径；订单取消/退款/测试单需有可解释的统计处理规则。不能盲目把所有订单行当成功销售。
- **时区与区间：** 订单时间、报表区间、导出时刻要有可确定的时区；无法确认时不允许生成精确的“昨天”或“过去七天”的报告。
- **货币：** P0 优先单店铺单币种；涉及不同币种时，必须有卖家确认的换算汇率、日期和来源才能做加总或利润排行，否则分币种展示。
- **来源可信度：** 支持预览原始单元格、关联失败的订单行、空 SKU、重复行、异常数量和缺失成本；修正数据后重新计算，不得静默自动补值。
- **批次可回退：** 误导入/重复导入可撤销该批次的派生统计和对应内部任务（涉及既有审批/审计时需保留必要痕迹），不会错误删除其他批次的独立记录。
- **客户隐私：** 商品销售和利润分析不得要求填写顾客姓名、详细地址、电话号码或邮箱；仅在客服核对和许可的外发功能确有需要时使用必要个人信息。

### 21.4 自然语言经营问数的最低事实标准

- 示例问题：“本月销量前五的 SKU？”需要店铺、时间、有效订单状态、订单行 SKU 与数量。
- 示例问题：“哪些 SKU 销量高却不挣钱？”至少需要已知订单行数量/净销售额、对应 SKU 单位采购成本、币种一致性；可回答“**已知商品毛利偏低**”，不能因缺平台费/广告/物流/税费仍宣称净亏损。
- 示例问题：“哪些物流成本异常？”若缺分 SKU 的运费数据，应回答“暂无足够物流费用明细，无法按 SKU 判断”，并指出需要补充哪些文件。
- Agent 应返回**所用业务口径、时间窗、命中记录数、缺失费用和原始行引用**；统计结果由确定性计算得出，不能依赖模型心算。

### 21.5 V1.0 补充：平台预设字段模板与可纠错的导入体验（P0 必须）

1. **可选模板：** 内置“通用商品文件”“通用订单行文件”，并提供 Amazon、Shopify 等候选平台的示例映射规则；**仅当模板已用对应合法样本验证字段与订单口径时，才能标注“已验证预设”**。TikTok 等模板按样本可得性补充。不能声称支持每一种报表版本。
2. **文件识别：** 结合列名、字段取值和用户指定来源建议“平台 + 报表类型 + 版本”；低置信度时显示候选而不是自动假定。没有识别到时进入通用映射模式。
3. **列名映射向导：** 显示原始列、目标业务字段、样例值、数据类型、必填情况和冲突提示；允许用户选择、修改、忽略列，并预览转换结果。可用下拉/选择实现，无须强制拖拽控件；功能正确性优先于形式。
4. **行级纠错：** 空订单号、重复订单行、金额格式、负数/退款、不同币种、时间格式、缺 SKU、无效数量、非法公式或未知状态必须逐行给出错误定位及修复入口；不得悄悄丢弃或补造核心数据。
5. **批次可复核：** 保存经过用户确认的映射规则及适用范围；重导入、纠错与覆盖更新应避免双重计数。用户可取消未提交导入；已入库批次撤销时必须处理其派生统计、待办和相关审计。
6. **文件安全：** 限制文件类型与大小，拒绝无法安全解析的文件；禁止执行 Office 宏、公式、脚本和外部链接；导出 CSV/Excel 时防范公式注入。控制可见的客户个人信息，检查上传内容中的提示词注入不能提高 Agent 权限。
7. **数据使用状态：** 为每次导入显示源文件、导出/覆盖时间、所属店铺、成功行数、失败行数、币种和“用户导入/合成/平台授权”身份。**成功读取文件不等于数据已验证，也不等于店铺已实时同步。**
8. **P0 验收素材：** 至少提供通用模板及两种不同风格的跨境卖家订单字段映射测试样本，外加取消、退款、缺失成本、重复订单、异币种、混合时间格式、恶意内容和不安全公式样本；真实样本未获授权时只能声称“合成格式测试通过”，不能冒称官方实测。

## 22. P0 Agent 真实执行能力与受控外发验证

### 22.1 必须证明的 Agent 行为

- 同一用户目标可以根据工具返回数据选择不同的下一步：有订单异常则创建待办，没有异常则记录“已检查”；有完整商品事实则提出 Listing 草稿，缺失则要求补录。
- 至少串联两种不同技能，并保留每一步的**输入来源、技能名称、业务校验、输出、任务结果**。不能把一个写死的聊天回复或静态脚本称为“自主智能体”。
- Agent **不能直接绕过工具声明**或自由修改商品/订单记录；输出是否执行由工具权限、店铺作用域和确定性业务规则共同决定。
- P0 内部可验证动作：真实创建关联指定订单/商品的待办或内部标签，保存一个经审核的 Listing 版本，执行后可在业务页面复查，重复运行不重复写入同一副作用。

### 22.2 真实外部动作的最小可控范围

**目的：** 证明 SoloOps 的 Agent 可以通过受控工具真正产生外部效果，而不冒险向真实买家发送错误消息。

- **必须有真实外发验证的功能路径：** 在卖家本人控制并已验证的邮件发送账号中，向卖家本人控制并验证的测试收件箱发送一份经营摘要或批准后的客服回复样例。
- **外发门禁：** 发送通道由用户主动连接；收件人必须属于预先明确的测试名单；展示地址、正文、次数和不可撤销性；经过单次明确审批，或者在仅针对测试名单的明示可撤销预授权下执行；发送频率和去重受系统限制。
- **成功定义：** 通道接受请求≠收件人已经收到。至少记录提供商提交状态；要宣称“已送达测试邮箱”，还必须由测试邮箱收件记录或可核实回执佐证；超时标记“结果未知”，核对后才能重试。
- **不可宣称：** 不能据此声称已接入 Amazon/TikTok 站内信、已向真实顾客自动回复或已完成平台侧退款与履约。

### 22.3 真实买家纯物流回复何时允许自动发送（P1 条件功能）

只对**一条**具备全部下列条件的真实消息开放被限定的预授权自动发送，默认仍为草稿：

1. 已连接的通信渠道允许此类商家主动/被动回复，并有具体发送权限；用户主动开启且可以立即撤销。
2. 能够可靠匹配一名客户、一个订单与相应履约状态；内容涉及多个订单或身份存疑则转人工。
3. 物流状态来自适用的可信数据源，更新时间满足卖家设置的时效阈值，且没有状态冲突；回复明确写“截至某时的信息”，不承诺未经证实的送达时间。
4. 消息仅包含允许自动处理的普通物流询问；有退款、索赔、地址变更、争议、威胁或政策冲突等任何并存意图时整条消息转人工。
5. 回复仅使用预审模板与已核验订单字段，检查收件人绑定、私人信息泄露、禁限宣传、语言和渠道规则。
6. 每个消息/版本的发送去重、生效配额、冷却时间、审计、失败查询、人工接管均可验证。

**任何条件不足就不自动发送。** 即使全部通过，它仍是受限 R2 行为，不能当作 R1，也不能绕过渠道身份与审批机制。

5. “自有测试邮箱真实外发”与“真实买家自动回复”是否严格区分；R2/R3 权限规则有无被弱化。
6. 第 17 节外部接口预评估有无不正确的绝对性断言，是否把官方文档、卖家授权和实际验证分别记录。
7. 七条 E2E 是否与四条 MVP 的子集映射一致，长期业务目标是否遗漏。
8. 知识库、报表、订单行、成本、客服混合意图、重复执行、外部结果未知、来源标注等风险是否有可验证的处理规则。

**本稿可以直接作为 Codex 的开发输入。** 功能需求已经冻结；Codex 自行完成必要且克制的交互、数据、接口与代码设计，先交付通过 A-01—A-32 的 P0，再逐步实施 P1/P2。真实平台授权、付费资源与高风险操作需用户明确许可；不能以示例数据冒充对外平台集成。

**文档终语（继承 V0.4 原则）：** V1.0 是以个人跨境卖家为主体的“Agent 原生完整功能需求与 Codex 开发交接”冻结基线。74 个长期需求保持原样，P0 数据入口、四条最低验收闭环及最终补充条款均已明确；**功能可被开发不等于已被开发，官方平台有 API 不等于本项目已取得授权，收发测试邮件不等于真实电商平台业务写入。**

## 25. V1.0 最终功能补充与 P0 交互验收边界

> 第 25—27 节是 V0.4 功能全集上的**最终增补**，不额外创建 SO 模块，不改变 SO 编号、P0/P1/P2 统计和原有七条 E2E。

### 25.1 P0 三个必须可完成的用户操作界面（功能要求，不是 UI 线框）

| 场景 | 用户必须能做的事情 | 系统必须反馈 | 不属于 P0 的范围 |
|---|---|---|---|
| **数据导入与映射向导** | 上传 CSV/Excel、选择或确认平台及报表类型、查看字段映射、纠错、预览、提交或取消 | 成功/失败行、币种时区、去重和缺失字段、真实导入批次；可返回原始数据 | 自动接管所有平台后台、适配未经验证的任意格式 |
| **Agent 驾驶舱 / AI 收件箱** | 看到上次巡检摘要、异常证据、待办、草稿、待审批、失败原因；启动/取消任务并查看进度 | 明示截至何时的数据、何时做过分析、各模块“已检查/缺数据/未检查”、任务真实状态 | 无数据时显示虚构实时仪表盘、自动无限巡检 |
| **审批详情与操作记录** | 查阅修改前后差异、对象、来源、风险、是否可回退，单项批准/拒绝/修改，查看运行结果 | 区分“仅草稿/本地已生效/外部已提交/外部已确认/结果未知”，展示审计记录 | 未授权直接改价、退款、发布或外发真实买家消息 |

应优先保证“用户理解下一步做什么、能看见事实证据、能发现失败”的体验，不追求复杂动效、三维图表或额外 UI 组件库。

### 25.2 运营任务的可见状态与反馈要求

- 每条消息或待办必须能关联具体店铺、订单、SKU 或导入批次，缺少可靠关联的必须标“待关联”。
- 任务允许用户查看“当前步骤、已经完成、等待输入/审批、发生了什么错误、如何恢复”，并提供合理的撤销/重试入口；不存在可保证回退时必须明说。
- Agent 主动发现的异常需要与被动问答区分：必须是**实际执行过巡检**并生成的结论；只读到历史文件时不能宣称已检查平台实时状态。
- 用户拒绝某项 R2 操作时，保留前序已获证实的分析与草稿，不得将整个历史记录连同证据删除。

### 25.3 业务数据验证优先级

| 数据类型 | P0 最少验证 | 不能做的结论 |
|---|---|---|
| 商品 | `店铺+SKU`、事实属性、价格及币种、已知单位成本 | 虚构认证、配件、规格 |
| 订单 | `店铺+订单+订单行`、数量、金额、状态、时间、币种 | 把取消/退款/未付款订单当作有效成交 |
| 库存 | 快照时间、可售数量（如有）、卖家设定阈值 | 没有快照时推断在库/断货 |
| 客服 | 消息原文、来源、时间、可验证订单关联、适用政策 | 混合退款意图自动外发物流回复 |
| 财务 | 有效收入、已知成本、归属规则、币种一致性 | 将“已知商品毛利”称完整净利润 |

### 25.4 用户可以接受的不完整行为

P0 允许“只用一类文件先完成对应业务”：例如只导入商品生成 Listing 草稿、只导入订单形成可核实的销售摘要；**但必须明确哪些能力因缺数据不能运行**。P0 不强制预先接入所有平台，也不强制卖家完善所有设置。

## 26. 开发前必须保持的业务可靠性规则

### 26.1 来源引用（Citation）必须是可点击/可查看的事实引用

- 对销量、利润、退款率、库存预警、价格比较等**事实型数值和结论**，提供可展开的来源明细。对于本地导入数据，引用可以是：数据集 ID / 文件名与导入批次 / 工作表或源文件行号 / 对应订单行或 SKU / 计算口径；不必依赖在线 URL。
- 原始文件行与规范化后的订单行需要保持可追踪关系。纠错或重新导入后，历史结论应明确已失效、需重新计算或已经重算。
- 使用确定性程序计算销售、费用、汇率与利润；LLM 可以解释和提出建议，但不能替代统计引擎。**对创意建议不强制伪造引用；对事实断言不可省略证据或不确定性标识。**
- 自然语言同一问题重复问数，验收关注筛选范围、数值和口径一致；不要求生成文本每个字完全一致。

### 26.2 Agent 熔断、阻断和可恢复状态

| 触发条件 | 需要的正确动作 | 禁止的错误动作 |
|---|---|---|
| R3、越权、策略拒绝 | 立即阻断该动作，记录规则与上下文并交人工处理 | 反复换工具尝试绕过 |
| 缺成本、订单状态、目标店铺等关键事实 | 暂停相关计算或操作，提示具体缺失字段 | 继续猜测事实 |
| 可安全重试的临时读操作失败 | 有界重试，默认不超过 3 次；超过上限熔断 | 无限递归调用 LLM/工具 |
| 对外写操作超时或回执异常 | 标记“结果未知”，查外部结果，确认前不重复写入 | 立即重复发送/发货/退款 |
| 多步任务超出步骤、时间或费用上限 | 暂停、保留已经完成的结果、通知卖家是否继续 | 继续消耗 Token 或重复产生副作用 |
| 用户拒绝审批或撤销授权 | 终止受影响的待执行操作，保留完整记录 | 把拒绝理解为“换一个工具执行” |

### 26.3 数据导入与 AI 系统的安全底线

- 未授权的来源文件内容、客户邮件、网页、评论和附件一律作为**不可信业务数据**；不能改变 Agent 的权限、系统配置或工具白名单。
- 文件解析不执行宏、公式、脚本，输出 CSV/Excel 时防止以 `=`、`+`、`-`、`@` 等开头的不可信内容触发公式解析；执行安全导出策略并保留原始值用于审计。
- 敏感密钥与客户个人信息须按最小必要原则存储、展示和送入模型；不得把生产凭据提交到 Git 仓库或发送到不相关第三方。
- 状态写入和外发动作支持去重/幂等与状态确认，保证“重试/刷新页面”不等于再执行一次。

## 28. 最低技术选型边界（按用户明确要求，保持克制）

> 这一节只规定技术方向和代码质量边界，**不提前指定数据库表、复杂系统架构、框架堆栈或微服务数量**。Codex 应自行做最小可行的技术判断，并在实施记录中说明。

### 28.1 技术方向

| 层级 | 用户期望与默认选择 | 控制原则 |
|---|---|---|
| **前端** | **Vue 3 + TypeScript**（建议优先于 JavaScript；Vite 为构建工具，不作为额外业务框架） | 只采用 Vue 这一套主前端框架；若坚持 JavaScript，也应通过 JSDoc/接口约束保持类型和可维护性。Vue 按用户“BOE”的前文语境暂定，不无故换成 React、Next.js、Nuxt。 |
| **后端** | **Python**，根据业务 API 需要选择一个轻量 Web 框架，首选 FastAPI，若有充分依据可选 Flask | FastAPI 与 Flask 不并用；业务逻辑放在清楚的 Python 模块和服务层，不全部堆在路由函数里。 |
| **数据库** | **必须使用持久化关系型数据库；默认 MySQL**（如已有适配合适的 PostgreSQL，需书面说明理由） | 订单行、商品、导入批次、任务、审批、审计、成本口径等为受控数据，不能只靠内存/JSON 文件；使用可追踪的版本迁移。 |
| **大模型接入** | 以可替换的 Python 模型客户端调用为主，优先使用官方 SDK 或必要的轻量适配层 | 不因项目名称叫 Agent 就强制堆 LangChain、LangGraph、MCP、复杂 RAG 框架；确有多步状态需求也优先验证简洁可测试方案。 |
| **自动化与长任务** | 先选可持久化状态、可恢复、可观测的简单机制；异步队列仅在真实需要时引入 | 不在首版同时部署 Redis、RabbitMQ、Celery、Kafka、工作流引擎等；不能用会随进程退出而丢任务的临时内存机制处理关键状态。 |
| **测试与规范工具** | Python 用 pytest；前端至少具备类型检查、单元测试和关键流程端到端测试 | 只引入必要测试工具，避免 pytest/unittest 混搭两套体系或多种 E2E 框架重复。 |

### 28.2 引入框架/依赖的审批准则

每引入一个**非必要或重量级依赖**，Codex 必须先在技术决策记录中用简短文字回答：

1. 解决了哪个确定的业务难题？
2. 标准库、已有依赖或少量清晰代码为何不足？
3. 它增加多少配置、运行服务、维护成本和安全面？
4. 有没有更简单的可测试替代方案？
5. 若将来替换，业务逻辑是否仍能保留？

原则：**以可读、可维护、可测试的模块化单体为默认**。不得为了技术关键词引入框架，也不得为了省依赖而重复造不安全的认证、密码散列或输入验证基础设施。

## 29. 代码规范、可维护性与交付质量（Codex 必须遵守）

### 29.1 可读性优先

- 所有代码应使熟悉 Vue/TypeScript/Python 的开发者能够通过文件名、函数名、类型和少量说明理解业务，不允许只追求“能跑”而生成难以维护的大型混合文件。
- 业务模块职责清楚：接口负责输入输出，业务服务负责业务规则，数据访问负责数据持久化，Agent/技能层只通过受控业务接口完成任务。避免 Controller 或路由直接承载大量 SQL、提示词、价格计算和审批逻辑。
- Python 遵守 PEP 8、必要的类型标注与明确的异常类型；TypeScript 开启严格类型检查，接口字段有稳定的类型定义。变量/函数使用有业务含义的名称；避免到处使用 `any`、魔法数字和晦涩缩写。
- **注释解释“为什么这样处理”，而不是把代码翻译成中文**：对金额口径、汇率日期、订单状态、异常规则、风控门禁、不可逆动作和 API 限制给出短而明确的说明；函数过长或条件分支过深时优先拆分，拒绝无意义抽象。
- 对重要复杂业务保留可读的中文业务说明或接口文档；日志能定位错误，但不得打印客户敏感信息或凭据。

### 29.2 工程质量底线

- 统一异常处理、参数校验、请求响应格式、权限校验与日志规范；不要出现广泛 `except: pass`、隐藏失败、忽略异常或“成功”假响应。
- 财务金额与汇率使用精确数值类型及明确舍入规则，不使用浮点数直接累加货币；SQL 查询参数化，外部输入严格校验。
- 数据库约束、幂等键及事务边界以防止重复导入、重复任务、重复订单行与重复审批执行；“外部结果未知”状态不能被业务代码自动覆盖成失败或成功。
- 样例数据必须标记为合成测试，生产流程不可默认返回伪造商品/订单/利润。所有模拟连接器应可识别、不可误指向真实店铺。
- 设置可靠的配置方式（环境变量、示例配置和必要的密钥管理说明）；代码库不得包含真实 Token、口令、支付凭据、客户数据或隐私文件。
- 每个核心功能同时提供正向、异常、边界与越权测试，关键问题修复要新增回归测试。发布前运行后端测试、前端检查和跨模块 E2E，并记录命令和实际结果。
- 代码依赖版本可追踪，数据库迁移可重复执行，新人可以按照 README 从零安装、导入样本、运行服务和复现四个 MVP。

### 29.3 明确禁止的开发行为

- 将整个后端写进一个 `main.py`，或者把整个前端堆成一个巨大组件；随意复制相似业务逻辑到多个模块。
- 为了显得高级，主动上微服务、消息中间件、复杂 Agent 框架、第三方插件市场或多种前后端框架。
- 使用模糊大段提示词代替可验证的业务规则、权限检查和确定性数据计算。
- 为满足表面验收在前端硬编码 AI 结果、订单、利润、API 成功状态，或跳过实际测试。
- 在未获授权的情况下擅自抓取受限平台、群发消息、真实退款、发货、消耗广告预算、删除仓库/旧项目数据。
- 在没有明确用户授权的前提下购买付费服务、部署到公开互联网或暴露测试店铺及敏感业务数据。

## 30. Codex 全盘执行交接协议（交付要求，而非在本文开发）

### 30.1 Codex 的职责

Codex 接手后，应独立负责**理解需求、审查仓库、制定最小技术方案、实现前后端、配置数据库、准备演示数据、编写测试、实际运行验证、修复问题、完善使用文档和报告进度**。本文件已经为业务功能、范围和验收建立约束，不应要求用户逐条设计接口或自行补写业务代码。

### 30.2 必须按顺序交付

1. **读取本文件与现有仓库**：建立 `SO → 优先级 → P0 切片 → 实现位置 → 测试证据 → 当前状态` 的追踪表；不得误把 V0.4 历史段落当作可以覆盖本 V1.0 冻结条款的指令。
2. **完成最小技术方案**：解释选择 Vue 3/TypeScript、Python 单一 Web 框架、关系型数据库、Agent 任务机制、最少依赖的理由；不输出庞大架构图后停工。
3. **先做导入与利润分析的真实原型**：完成平台/通用 CSV 映射、订单行计算、异常文件处理、可追溯利润问数，并以自动化测试证明正确性。
4. **依次完成四个 P0 MVP**：MVP-04 经营问数 → MVP-02 Listing → MVP-03 客服 → MVP-01 今日运营；实现三项用户操作界面和审批，并执行第 23 节全部 32 项验收（不适用/授权阻塞须如实注明）。

### 30.3 自主执行与求助边界

- Codex 可自主决定常规文件组织、UI 细节、纯本地低风险修改和必要测试，实现中应不断提交清晰的进度记录，尽量不反复询问非关键偏好。
- 但以下事项必须停下并获得用户明确许可：需要真实账号/密钥、对外发信给真实买家、平台正式店铺写入、退款/支付/广告扣费、采购下单、删除原有用户数据、公开部署、购买付费资源，以及与冻结需求相矛盾的重大改动。
- 若遇缺少 API 资格、真实样本或资源，Codex 应记录可复现阻塞、完成不依赖该条件的其他工作并提供清晰下一步；不得绕过授权、编造证据或私自降低验收标准。
- 如仓库已有代码或数据，先检查并保留；未经明确指示不得清空仓库、历史记录、环境依赖或真实业务文件。若具备合法的仓库写权限，可在本地检查通过后按阶段提交，未经授权不强制推送远端。
