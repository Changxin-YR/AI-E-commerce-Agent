## 0. 对 Zeke 评审意见的采纳与必要纠正

| 风险 | 决议 | R2 的实际限制 |
|---|---|---|
| A1 导入适配成本过高 | 采纳，分层验收 | 先做好通用映射与人工纠错，再补安全分批，平台预设只针对核实过的报表格式；不为每个渠道无限增加解析规则 |
| A2 历史成本演变成复杂会计系统 | 完全采纳 | 本轮仅支持“当前采购成本回推估算”和“卖家提供依据的订单行历史成本”；不做 FIFO、移动加权平均、采购批次财务总账 |
| B1 任务状态机容易重写成意大利面条 | 采纳风险，纠正实施前提 | **现有** `agent.py` / MySQL 已有任务状态、步骤、技能契约和审批等基础；先核对并复用，缺什么补什么，禁止平行新建一套状态机 |
| A4 五类导航可能破坏路由 | 完全采纳 | 只分组导航及调整工作台呈现，现有 URL、组件、查询参数、旧深链和浏览器历史都必须继续可用 |
| 用 CI 证明交付 | 采纳但补足 | CI 在目标提交上成功是**必要条件而非唯一充分条件**；还要有实际业务数据/脱敏或合成数据对账、API/界面回读、失败与回滚证据 |

**补充纠正：** “低毛利”不是“需要修改 Listing”的因果证据。跨技能流程必须先判断数据是否完整，分别提供成本/费用核查、商品内容核查或人工补证分支。Agent 没有足够证据时可以合法地停止，不必为了展示执行而生成没有依据的营销方案。

## 1. 目标、范围与完成定义

### 1.1 本轮唯一目标

让个人跨境卖家在**无实时平台 API**前提下，使用自主导出的 CSV/Excel 和必要的人工录入，完成以下实际业务路径：

**导入报表 → 核对字段/状态/数据身份 → 自动发现异常 → 查看可追溯指标和缺失项 → Agent 选择可行的内部操作 → 用户审批 → 保存真实内部业务结果 → 新数据导入后复检 → 导出可手工使用的成果。**

目标是“一个人能够真正完成工作”，不是“多做一些页面、多跑几个模型请求”。

### 1.2 明确不做

- 不启动 47 个未实现的长期 SO 模块；不新增一个 ERP 子系统或多租户付费平台。
- 不做 Amazon/Shopify/TikTok 的未授权写入、同步、退款、自动发货、自动调价、广告支出、真实买家自动外发；QQ 测试摘要通道不算平台客服通道。
- 不做采购批次 FIFO、移动平均、库存财务总账、跨境税务自动申报、通用会计系统。
- 不做自动适配所有年份/地区/版本的全部电商平台报表；没有格式证据不称“官方模板已支持”。
- 不另起一套 Agent 框架、工作流引擎、微服务或 Skills 插件市场；不为代码行数单独展开全面重构。
- 不在未授权情况下进行新的付费模型调用、QQ/其他邮件实际发送或真实客户数据上传。

### 1.3 已有能力，不得重复造轮子

- Vue 3 + TypeScript、FastAPI + Python、MySQL；接口 / Service / Repository 分层。
- 已有商品、订单、消息、库存、账单等文件导入和手工映射基础；既有批次、版本、撤销、溯源和导入错误列表。
- 已有 Agent 技能契约、固定流程、持久步骤、预算、审批、R0–R3 权限、来源时效、幂等和结果核验。
- 已有 Listing 草稿及本地审批、客服消息与草稿、经营问数、运营待办、报告、QQ 测试邮箱验证。
- **当前提交的历史证据：** CI 719 个后端测试、98 个前端单测、59 个浏览器 E2E 成功；仅说明已有基线，开工后的所有变更仍须重新验证。

### 1.4 完成判断

功能“完成”必须同时满足：输入可操作、业务结果正确、证据可回查、失败可解释、权限不被绕过、相应自动化测试通过、目标提交 CI 成功，且有人从卖家视角完成至少一条真实操作路径（在没有真实文件时只可声称“合成场景完成”）。

## 2. 工作包与停工规则（唯一执行顺序）

| 序号 | 工作包 | 本轮交付重点 | 进入下一包门槛 |
|---|---|---|---|
| A0 | 实施前只读基线检查 | 校验 HEAD、工作区、分支、CI、迁移、数据保护、现有功能 | 交付基线/风险报告，用户同意后才进入 A1 |
| A1-1 | 通用数据导入最小闭环 | 字段映射、人工纠错、金额/状态歧义审阅、导入对账 | S1/S2/S4/S6 核心用例通过，正确性没有阻断缺陷 |
| A1-2 | 大报表安全分批 | 超限引导/安全拆分或分片、跨批次去重、撤销及恢复 | 超过当前 2000 行样本完整核对，不能重复计数或静默丢行 |
| A1-3 | 经证实的渠道预设 | 只增加拿到格式证据的 Amazon/Shopify 等模板 | 有确证格式的模板通过测试；暂无可靠资料时明确将 A1-3 标为「条件未满足，延期」，不阻塞已完成 A1-1/A1-2 后进入 A2 |
| A2 | 历史成本和利润口径 | 当前成本估算 + 卖家订单行成本录入，两类结果分清 | 金额、退款、成本变化、来源、旧报告稳定性与拒绝误导测试通过 |
| A3 | 异常事项复核闭环 | 核对≠解决，保存依据，来源更新后复检 | 低库存/履约/低毛利/客服至少四类状态转换通过 |
| A4 | 个人卖家 AI 驾驶舱 | 将 18 个功能入口分为约 5 个业务分组，减少操作路径 | 全部旧路由及深链可用；桌面与 390px 手机 E2E 通过 |
| B1 | 受控跨技能 Agent 最小组合 | 在已有持久状态/Skill 上增加一条证据驱动分支 | 至少两种技能真实运行、至少一项可核验内部写入；含失败/重启/拒绝用例 |
| B2 | Listing 人工交付 | 审批版本复制/通用草稿导出 | 内容、来源、状态、安全转义与手工使用路径正确 |
| B3 | 客服人工交付 | 草稿复制/导出、人工操作证据、外发状态诚实 | 混合意图、隐私、政策不全时禁止自动对外发送 |
| C | 工程与上线门禁（按条件） | 调度运行状态、局部可维护性、公网或真实个人数据前安全检查 | 未达到安全门槛，不允许以生产就绪名义发布 |

**硬性停点：** 一个工作包完成后，Codex 必须停止继续开发、提交独立验收报告和提交 SHA，等待用户开启下一包；不得因为 A1-1 通过就自行连做 A1-2、A1-3、A2。**A0 不写业务代码。**

**避免重复评审：** 一般性的实现细节和测试样本选择由 Codex 独立决策；只有数据破坏、历史口径变更、外部付费/写入、新依赖/架构变更和无法克服的业务歧义需要用户审批。

## 3. 各工作包精确定义

### A0｜只读实施基线与安全保护

**必须做：**
1. 只读核对 `git status`、实际 `HEAD`、工作分支、远程状态、最新 CI，保留用户未提交修改；不得假设历史审计 SHA 仍是最新。
2. 阅读 `AGENTS.md`、V1.0 冻结 PRD、`docs/foundation-release.md`、`docs/feature-matrix.md`、`docs/foundation-acceptance.md`、相关测试和当前实际源码。
3. 核对真正会触及的导入/利润/待办/Agent 代码和已存在的数据结构，指出可复用组件、旧迁移与状态约束。
4. 确认隔离测试库规则、开发数据保护边界、备份与恢复工具是否可用，不连接/重置真实业务库。
5. 输出一页：`基线 SHA / 工作区状态 / 现有 CI / 本轮禁止破坏项 / 修改影响范围 / 数据保护与回退 / 外部授权限制 / A1-1 最小建议`。

**停止点：** 仅提交核查结果给用户。未经明确批准，不开始 A1-1、不执行破坏性 DB 操作、不安装新框架、不调用付费模型或真实邮箱。

### A1-1｜通用映射与脏数据纠错【第一代码工作包】

**关联：** F-02；SO-001、008、027、041。复用 `import_catalog.py`、`import_parser.py`、`imports.py`、已有映射 UI / API。  
**操作闭环：** 文件上传 → 报表类型选择/候选识别 → 列映射 → 原始值与标准值预览 → 人工确认歧义 → 错误行纠正 → 提交 → 导入结果对账。

**本包必做：**
- 保留现有安全输入边界：UTF-8/带 BOM、单工作表 XLSX、2 MiB/2000 行/64 列等；对真实卖家常见非 UTF-8（例如 GB18030）、多表头/多工作表只提供明确的选择或转换指引，除非经测试证实可安全局部加入，不默认增加全能解析器。
- 支持字段人工映射并保存个人模板；字段匹配不确定时提醒，不凭相似名称自动决定“总价 vs 单价”“整单退款 vs 订单行退款”“负数 vs 正向记录”“时区/币种/状态”。
- 发现缺稳定订单行标识、重复键、退款口径不明、成本币种不符、时间不完整时，应阻止不可靠的汇总或明确呈现“待纠错”，不能静默补造业务事实。
- 对比提交前后的行数及状态，提供源记录数、有效数、错误/重复/覆盖数与可导出错误原因。发现已有功能已经满足要求，应只补测试/提示，不重复改写。

**通过：** S1 正常多 SKU、S2 取消/退款/重复及错列、S4 币种/时区歧义、S6 不可信单元格。单次安全边界无需在 A1-1 扩大。至少一条合成文件从上传至保存后再次读取正确，金额逐行对账；用户手动改映射不需修改原始表头。

### A1-2｜安全分批导入【与 A1-1 分开提交】

**目标：** 卖家持有超过现行 2000 行 / 2 MiB 文件时存在安全、易理解的完成路径，不以无限增加内存和单请求时长实现。  
**允许路径：** 小型本地安全拆分辅助工具 + 既有上传/映射/批次能力；或经过审计的受限分片/流式导入。由 Codex 说明选择最小方案的理由，不强制先做大型后台任务系统。

**必须验证：**
- 生成批次归属及总行数对账，跨文件重叠行去重不重复累加；来源身份、店铺、渠道、金额口径保持一致。
- 错误分片可以核对并恢复，已成功的分片不因重试重复计入；撤销单个批次及撤销整组都应遵守现有数据保护规则。
- **部分成功不能默默呈现为全量报告。** 导入组未全部完成时，涉及全量判断的分析结果标记“部分覆盖/数据不足”。
- 对 2001 行以上、多订单行、跨文件订单、重复键、失败重试、取消与恢复分别留测试证据。

**停止点：** 完成分批功能和必要测试，不开始新平台格式解析。真实大文件尚未提供时只声明合成超限用例通过。

### A1-3｜经核实的平台模板【模板存在证据才做】

**目标：** 在通用映射已经稳定的前提下，内置有实际格式依据的 Amazon / Shopify 报表映射。  
**要求：** 每份模板记录`平台/报表类型/版本或日期/原始字段示例/字段含义/验证方式`；数据歧义保持候选映射；模板随平台格式变化可失效，不影响用户手动映射。

**门槛：** 未获取真实脱敏文件 S7 或官方可靠的格式证据，不能称“已兼容所有 Amazon/Shopify 报表”；可以以“模板待证实、A1-3 条件延期”结束本包，**不阻塞 A2**，避免为了填进度凭空捏造列名。

### A2｜历史成本与利润口径【只做最小两模式】

**关联：** F-05；SO-052、053、054、055、056、057、059。  
**禁止：** 新建企业会计系统、FIFO、移动平均、跨仓采购批次、自动生成历史成本、默认根据现值推断过去为真实成本。

**仅两种成本来源：**
1. **按当前单位采购成本回推历史订单的估算模式**（沿用现有计算，但必须明确在报告与 UI 中展示“当前成本回推估算，非订单时点实际采购成本”）。
2. **用户手动为特定订单行提交历史单位成本与凭据来源/时间/币种的模式**。该数值是“卖家提供并确认的历史成本依据”，不是系统独立验证的会计事实；须能修改、撤销、追踪版本，不覆盖原始导入行。不存在可靠凭据时保留“未知”。

**要求：**
- 支持同一 SKU 不同订单时点成本不同，不把商品现价改动倒灌成历史事实。
- 原有销售额、行折扣、退款、订单状态、订单行数量与当前成本来源的计算保持一致；如果现有口径存在应修复的实错，单列回归与版本迁移影响。
- 财务展示固定区分`可确认净销售额`、`当前成本估算的商品毛利`、`按卖家确认历史成本计算的商品毛利`、`费用缺失`、`尚无法核实净利润`。不存在完整费用证据时不能称精确净利润或完整 COGS。
- 不因同一费用已在账单和人工费用中出现就重复计入；不能确定订单费用分摊时明确“费用待核”，不进行隐式分摊；不为了“显示数字”偷偷填 0 或假汇率。
- 历史分析版本保持原口径和来源；新增用户成本依据后，原报告应显示旧依据/待重算，新口径另生成可追溯结果。

**通过：** 同 SKU 两个历史订单不同成本、未录入历史成本、部分退款、异币种、无折扣、重复费用、历史口径版本以及用户撤销成本凭据；结果能展开原始订单行、采购成本、计算公式、来源状态。金额采用 `Decimal` / `Numeric`。

### A3｜异常待办真实业务状态

**关联：** F-04；SO-004/005/030/068。  
**禁止：** 只新增“业务已解决”按钮而没有证据或复检；不能将“人工已核对”自动当作外部发货、补货、退款成功。

**最低业务状态：** 待核对 / 已核对待外部处理 / 已登记操作证据 / 待来源更新复检 / 新有效证据支持已解决 / 已忽略或不适用。可视为旧状态上的解释或必要的局部扩展，不强制重建整个表或状态机。

**要求：** 处理记录和原始异常关联 SKU/订单/店铺/来源批次；外部处理可记录卖家人工说明及来源但保留自报性质；新数据导入后对对应问题重新检查，只有可验证对应对象且数据更新时间足够新才可宣称已解决。记录缺失、时间过期和跨渠道不匹配必须显示待复核。旧已完成记录迁移或兼容显示，不可消失。

**通过：** 低库存、履约、低毛利、客服四类异常：无新数据、数据更新仍异常、数据更新且异常解除、误点完成重开、重复运行、来源撤销/清除，全部能显示正确处理状态和审计。

### A4｜以卖家任务为中心的 UI 简化

**关联：** F-01；SO-002/003/004/005/065/067/068。  
**仅调整入口和交互，不更换前端框架、不删业务页、不改 URL。**

**顶层导航建议五类：** `今日 AI 运营`、`商品与选品`、`订单与客服`、`经营与财务`、`自动化与设置`。所含子入口可以继续指向全部现有路由；长线尚未开发的功能不得出现可点击的伪页面。

**核心首页：** 数据身份及导出截至时间；`待我处理`、`AI 已完成`、`需要更新数据` 三类工作收件箱；清晰“导入文件 / 一键检查 / 继续审批”入口；聚合来源、店铺、金额、币种、任务状态不能丢。默认选择已有店铺与合理时区等已知参数，高级模型预算/规则保持可查看与编辑，但先收纳在展开区。

**回归门槛：** 旧的至少 18 个功能入口均可达、旧路由和带查询参数的深链可达、浏览器前进后退、跳转后对象身份正确；1440px 桌面与 390px 手机关键流程端到端实测；无关键按钮空转、状态误导和横向溢出。只隐藏菜单但用户找不到原功能不算完成。

### B1｜已有 Agent 的“受控跨技能组合”【先做设计核对，再开发】

**关联：** F-03；SO-003/004/005/018/053/057/060/062/066/067/068。  
**先提交短设计核对：** 现有持久任务实体和步骤、已有状态、每个技能输入输出、权限级别、预算/幂等/熔断、何处加入条件分支；必须说明为何无需另起流程引擎。如确须新增状态字段，只补必要迁移及回读测试。

**唯一新增示范场景：** “分析最近 7 天低毛利商品，基于证据提出下一步并执行允许的内部操作。”
- 数据/成本缺失 → 请求补录或创建核对待办，避免编造归因。
- 有可信的费用/采购成本证据 → 形成费用核对或定价分析**草稿**（非真实改价）。
- 商品内容本身被确证缺少必要参数 → 由现有 Listing Skill 生成候选，审批后本地保存版本，但不宣传“修 Listing 就能修毛利”。
- 多个问题并存 → 展示多条有限建议，风险和证据分别标注；无法确认因果时转人工。

**受控条件：** 白名单、输入输出契约、店铺作用域、来源快照、确定性计算、R0–R3、审批、单次预算/步骤/时间、有限重试及未知结果回查；R3 即刻拦截；不可让模型自行扩工具权限或修改业务表。

**通过：** 四组事实驱动不同分支，至少 2 个内置 Skill 真正调用，至少 1 项经审批实际保存内部业务记录，并可重启回读；来源变更阻止旧审批、重复请求不重复副作用、缺权限阻断、用户拒绝不会变成已执行、成本预算不足暂停、死循环被熔断。没有新增全能自主 Agent 的要求。

### B2｜Listing 人工可使用成果

**关联：** F-06、SO-018；保留 SO-015 为未来真实刊登。  
**实现：** 已批准内容一键复制或下载包含店铺、SKU、市场、文案版本、来源、标题、说明、缺失属性提示的**通用草稿**；平台特定模板必须有针对指定平台/站点/类目/版本的真实格式依据和独立验证才可标注；未经 API 不称发布。

**通过：** 完整中文与英文内容不乱码，CSV 输出防公式注入，版本和来源正确，缺 SKU/GTIN/认证不能自动伪造；数据变更的失效草稿明确提示，不得继续以最新版本名义导出。

### B3｜客服草稿人工可使用成果

**关联：** F-07、SO-031/032/033；未来 SO-034/035 仍保留。  
**实现：** 合法授权范围内复制/导出已审回复草稿，附原消息索引、订单关联、适用政策/有效期、目标语言和需人工接管原因；复制和导出均不自动改变“平台未发送”的事实状态。卖家可单独登记人工在原渠道操作的时间、方式与证据；自报标识不等于平台回执。

**通过：** 物流+退款混合意图不自动外发；订单身份无法核验或物流过期时保留不确定提示；跨店铺权限与个人信息泄露测试通过；QQ 测试外发的历史回执不冒充真实买家沟通证明。

## 4. 全轮测试数据与验收证据

### 4.1 固定最小样本

- **S1 正常商品/订单**：同订单多 SKU，数量、单价、折扣、币种/成本。
- **S2 脏数据**：取消、待付款、部分退款、整单退款歧义、重复行/重复批次/重导、错误金额列、订单行标识不稳定。
- **S3 成本**：同 SKU 多时点订单行人工成本、当前成本变化、未知成本、人工费用和平台账单交叉费用。
- **S4 币种/时间**：USD/EUR/CNY 多币种、跨时区、日期截断、缺汇率、缺时区。
- **S5 异常/客服**：低库存、过期快照、异常未解除、物流+退款、身份未核实、过期政策。
- **S6 恶意/失败**：Excel 宏/公式/外链、CSV 公式、上传越界、Prompt 注入、跨店越权、超时未知、并发重复、服务重启。
- **S7 真实脱敏文件（有条件）**：用户合法提供、来源与格式可核实的 Amazon/Shopify 等报表。没有 S7 时，只能报告“合成格式通过；真实卖家兼容仍待验证”。

### 4.2 证据最低要求

每个工作包的报告必须包含：

1. `实际 HEAD SHA`、本包修改文件及差异摘要、风险与是否新迁移。
2. 场景输入来源（合成/用户导入脱敏/官方开发环境）、记录数及预期值；不得提交真实文件或个人秘密至公开仓库。
3. 单元/集成/前端/浏览器检查命令、运行环境、**实际**通过/失败数、固定校验值或业务对象状态回读；保留失败后修复证据。
4. 数据库迁移和回退（如本包涉及）、测试隔离库及原有记录保护证据。
5. 目标提交的 GitHub CI 链接与结论。**CI 成功是必要但不足**：仍需要一条卖家视角端到端操作证明用户真的完成事情。
6. 本包未完成的条件、风险、权限限制；下一包的前置条件说明。

**严格禁止：** 复制前一提交的 CI 结论冒充本次通过；通过修改断言掩盖数据错误；把模拟平台写入当作真实平台成功；拿历史邮件测试许可再执行真实发送。

### 4.3 最终统一卖家旅程（只有 B3 后才整体判定）

店铺建立 → 导入数据与纠错 → 查看收入/成本/已知毛利及依据 → AI 找到异常 → 保存待办/分支选择 → 人工批准内部变更 → 查看操作版本 → 导入更新后复检 → 复制或导出 Listing / 客服草稿用于**人工**工作。所有环节在本地数据库真正回读，刷新与重启状态一致。

## 5. 使用和授权边界

- **技术基线固定：** Vue 3 + TypeScript、FastAPI/Python、MySQL；保留既有分层、项目运行指令、迁移和测试体系，非必要不安装新库。
