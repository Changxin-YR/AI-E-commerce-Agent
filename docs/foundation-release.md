## 1. 交付目标与优先级

交付一个可以实际安装、使用、重启恢复和维护的个人卖家运营基础系统。以完整业务过程为交付单位，先完成基础版本，再按路线图迭代扩展功能。

本次用户确认的优先级覆盖此前按全部长期功能依次开发的顺序。现有 74 项长期需求、32 项原验收和历史实现证据保留；基础版本范围由本文约束。尚未实现的扩展模块暂缓开发，已有功能继续可用并接受必要的回归修复。

基础流程所必需的依赖、交互、异常处理和验收不能因“暂缓扩展”而省略。发现依赖缺口时，应在当前版本内补齐完整的基础业务能力，说明依赖关系；不得用占位页面、固定假响应或标记完成代替实现。

## 2. 基础版本的业务定位

服务个人卖家，通过有明确来源的文件和人工资料维护商品、订单、库存及客户消息，完成经营检查、分析、商品文案维护和客服处理。每项结论可追溯，每项写操作有明确权限，每项任务可以处理到有业务意义的结束状态。

CSV/Excel 是本版本正式支持的数据入口。用户明确选择店铺、渠道、币种、时区和数据身份。导出格式相似仅表示可做字段映射，不能标为已经接入相应平台。

四条主要业务流程共用商品、订单、来源、任务和审批记录。首页能找到待处理事项，并进入正确店铺、对象和处理页面。处理后回到任务或原对象可确认结果，刷新、重新登录和服务重启后状态一致。

基础版本交付还包括受控的真实模型验收，以及原 P0-External 规定的本人测试邮箱真实送达验收。平台 API 同步、平台商品发布、真实买家自动发送等另按后续迭代实施；界面和文档准确表达当前动作作用的位置。

## 4. 四条业务闭环

### F-01 今日运营与异常处理

1. 建立店铺并导入资料，核对映射、错误行、重复和最终记录数。
2. 明确检查范围、经营规则、订单时间窗及库存时效，展示各分支是否有可用数据。
3. Agent 读取受控服务的检查结果，组织解释，展示事实、缺口与全部候选。
4. 用户审批后保存真实检查和待办；未审批的候选不能冒充已执行动作。
5. 从待办进入对应商品、订单、消息或分析页面，查看证据并完成处理或记录核对结论。需要补充来源时，经导入或现有修订入口更新，再重新检查。
6. 可完成、延期、忽略、重开，并保留处理说明。手动“完成核对”不等同于平台订单已发货、库存已补齐或异常已经消失。
7. 重复检查不重复建任务；来源变化导致旧审批失效；新检查反映最新来源。刷新及重启后保留正确状态。

### F-02 经营问数与可追溯决策

1. 对已有订单与成本选择明确范围，输入业务问题。
2. 模型理解受支持的意图；范围不清或暂不支持时给出明确补充要求，不编造查询结果。
3. 由业务服务计算金额、数量、毛利和缺口，模型组织解释；相同数据和口径重复计算一致。
4. 用户能展开公式、原始订单行、成本来源、币种和未知费用，查看结论为何成立。
5. 需要处理的结果经审批保存为分析及待办，并能从待办回到对应分析和业务对象。
6. 完成或重开待办、补充数据后重算；旧结果显示来源变化。保存、回读、刷新、取消和失败恢复均有可验证记录。

### F-03 商品 Listing 维护

1. 选择有来源的商品事实和目标，确认本次模型数据范围及预算。
2. 真实模型生成符合当前产品契约的候选；列出缺失事实，保留完整商品名和参数依据。
3. 用户比较、编辑并保存待审版本；事实性新增需有依据，不能由模型补出认证、材质或营销效果。
4. 批准或拒绝当前版本；批准后本地有效版本实际变化，并可回读新旧版本和审计记录。
5. 历史内容可按现有机制另存并重新审批；来源覆盖、撤销或清除后相关状态一致。
6. 从运营或商品入口进入时保留正确店铺及 SKU；完成后可返回关联事项，确认本地维护结果。平台发布状态保持真实。

### F-04 客服处理与受控外发

1. 导入或录入消息，选择正确客户问题、已核验订单和有效政策，保留原文与出处。
2. 模型识别意图，结合受控事实和政策生成候选；退款等敏感诉求进入人工处理，物流未知时不作承诺。
3. 用户审阅、编辑、批准并保存草稿或人工处理结论；可回读消息、版本、依据及处理状态。
4. 未发送的回复显示为草稿/待发送；“已存档”不代表客户已经收到。需要人工渠道处理时，记录人工处理事实及证据，不伪造系统发送回执。
5. 完成原定 P0-External：通过已实现的 R2 摘要通道，将一份有来源的经营报告，经全文审阅和单次批准，真实发送至本人控制且已验证的测试邮箱。保留提交回执和实际收件佐证。
6. R2 当前验证经营摘要通道；客服草稿和平台消息发送分别记录状态。若现有实现存在混淆，必须修复。
7. 超时保留未知，按现有协议安全回查；不自动重复发送。撤销、在途变化、来源失效和记录清除遵循现有边界。

## 5. 贯通验收场景

使用同一组明确标记的合成店铺资料，完成以下连续操作；后续取得合法真实样本时，用相同验收口径复验：

建店与导入 → 今日运营发现低毛利/待核订单/库存或消息问题 → 进入分析查看计算依据 → 保存并处理待办 → 定位同一商品生成并批准 Listing → 对同一数据集中的客户问题完成客服处理 → 保存经营报告 → 审阅并发送一封本人测试邮件 → 回读任务、版本、报告、发送回执和收件证据。

对同一组数据补充或修订一项来源，再验证旧结果失效、新结果更新及已处理历史仍可解释。另验证重复点击、断线、刷新与服务重启。各页面间不得丢失店铺、数据身份、渠道或对象上下文。

样本由项目维护，覆盖正常、缺成本、退款、混合币种、重复订单、库存过期和客服混合意图。优先复用现有 examples/imports，补齐政策和预期结果清单。统一样本时间、查询窗口、政策有效期和库存时效；若提供生成脚本，明确标记合成数据，禁止修改真实来源时间。

## 6. 基础工程与用户使用要求

- 沿用 Vue 3 + TypeScript、FastAPI/Python、MySQL，保持接口、业务服务、数据访问三层。Agent 调用受控业务服务；金额使用 Decimal/Numeric，时间存 UTC、显示明确时区。
- 账号、会话、用户与店铺隔离、CSRF 和输入校验继续有效。错误信息提供可执行的下一步，失败不得显示成功或留下误导性旧正文。
- 前端沿用现有设计。补齐必需的入口、空状态、加载、错误、重试、确认及结果反馈；桌面与手机关键流程可用。导航和术语保持一致。
- 数据和任务持久化；重启恢复后不重复执行已审批动作。定时任务行为与 API 实际运行条件一致，错过周期、暂停与失败可读。
- 提供经过执行核验的首次安装、配置、迁移、创建账号、启动、关闭及升级说明。密钥只通过忽略的本机配置提供，示例配置说明字段含义。
- 提供数据库备份与恢复操作说明，并用隔离合成数据库验证一次恢复及代表性记录回读；不改动、清空或恢复覆盖用户真实业务库。若已有工具足够，复用现有工具。
- 清除操作准确说明影响及回退边界，保留必要审计。日志能定位错误且不暴露密钥、会话、客户正文和完整模型请求。

## 7. 真实模型、外发与资料条件

本轮追加真实模型调用已获用户明确授权：累计人民币 1 元封顶，仅使用合成数据，使用项目已配置的百炼通道。实施方应维护本轮累计费用记录，按已核实费率和保守预算控制每次调用，接近上限时停止追加调用；费用未知时保留未知并先核对。此次授权仅覆盖本轮模型验收，邮件发送许可单独确认。

本轮真实模型验收仅使用明确标记的合成业务数据，覆盖四条流程的成功路径，以及缺证据、敏感意图、来源变化等关键边界。复用已有协议测试覆盖其余故障，避免无目的扩大真实调用。记录模型、时间、脱敏结果、实际已知费用和结论；失败先定位，控制重试。

真实邮件验收需本人发送账号、通道配置、已验证的本人测试收件邮箱及本次发送授权。先完成配置指引和可执行的审批页面，再进行真实提交。不得沿用历史许可向其他地址发送。

缺真实模型或邮件条件时，其余基础工作继续；验收表保留准确阻塞和所需输入。基础版本最终完成状态须反映这些必验项，不能将其删掉或改用替身通过。真实店铺文件暂缺不妨碍合成样本验收，但必须如实记录尚未做真实经营数据验收。
