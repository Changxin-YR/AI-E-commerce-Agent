# SoloOps 开发文档

## R2 A2：订单行成本凭据与两种利润口径（2026-10-10）

CI揭示成本写入与页面重算的异步竞态：凭据编辑器原本只禁用自身表单，重算可在撤销提交前读取旧成本。现由OrderCostEditor的working事件经AnalysisEvidence传播，AnalyticsView合并写入与刷新忙碌状态，在写入及随后版本回读完成前禁止重算/切店。端到端受控延迟请求验证此窗口，金额与旧快照断言保持。

`order_costs` 的接口只调用服务，服务在用户→店铺锁下复核源行、店铺 revision、成本 expected_version 和请求 UUID；仓库负责作用域查询及追加记录。`order_cost_revisions` 使用 Numeric(18,4) 保存单位成本、UTC 保存凭据/操作时间，旧版本保留。每个源行最多100次录入/修订，仍可撤销；原订单导入内容不变。凭据说明是卖家自报，确认动作与所提交版本绑定，审计只保存操作编号和版本。

`AnalysisInput.cost_mode` 默认 current_estimate；seller_history 只读对应源行的有效凭据。净销售额、订单状态、行折扣、行退款和原购买数量公式保持；缺成本或异币种不退回当前商品成本，不造汇率。退款不恢复采购成本或库存。计算版本2写入新快照，旧版本默认1并保留原公式/金额。商品主档成本变更不改写人工历史凭据；成本修改/撤销使旧分析、审批和相关派生结果待重算。

订单覆盖/撤销后，已不在当前投影的凭据置stale；撤销覆盖批次恢复旧源行时不会恢复旧确认。清除源批次先清空凭据金额、币种、说明、时间及源行外键，再沿既有分析依赖清除快照并删除源行。保留无正文的成本审计行。迁移b37e820ca491只新增一表，有任何成本历史时在DDL前拒绝降级，空表可回退/升级；旧库需按维护流程备份并核实升级授权。

前端在经营分析中切换模式、展开订单行录入/修订/撤销并看版本；金额使用文本输入保留Decimal精度，修改表单清除确认，未知失败用同一UUID重试。分析页显示可确认净销售额、所选成本商品毛利及费用缺口，并链接人工费用/渠道账单核对。同一费用的重复/分摊核对继续由现有服务处理，商品毛利不自动扣减台账或账单，净利润仍未知。今日运营、总览与AI问数继续用明确标注的当前成本估算；OperationScope限制该口径，历史模式在经营分析中直接运行。

## R2 A1-3：有依据的渠道字段候选（2026-10-10）

`import_presets.py`集中维护当前Shopify商品CSV的字段映射、官方URL、核实日期和使用边界。匹配同时要求报表类型、来源渠道以及区分大小写的5列表头签名；新增`BatchOutput.presets`仅为派生响应。接口和仓储协议沿用原导入三层，候选展示不写业务数据。`ACTIVE_PRESET_IDS`可停用过时格式，已保存的映射和原始/修正/规范化值仍按原批次读取。

`ImportPresets.vue`用现有设计显示字段对应、证据和补录步骤。卖家应用后只改变本地映射草稿，同时清空旧修正/审阅/覆盖许可，再走ImportService原预览、逐行纠错、语义确认、提交和撤销。币种不使用店铺默认值猜测，空白变体名不向下填充，未知成本不填零。预设不自动纳入商品描述、国际售价或比较价；未映射的危险单元格仍由原解析/校验链阻断。

官方订单资料尚不足以形成满足本地行级语义的自动预设，条件与核实依据见references及[r2-a1-3-acceptance](r2-a1-3-acceptance.md)。实现无新表/迁移/依赖，复用原始批次隐私清理及隔离检查。

## R2 A1-2：导入组、恢复与覆盖门禁（2026-10-10）

采用本地受限拆分工具 `backend/scripts/split_import.py` 和现有 ImportService。按CSV逻辑记录划片，UTF-8/BOM、中文和引号内换行保持；按编码后字节数及数据行数双限生成文件。所有分片均通过原parse_file后才生成manifest.json；失败只清理本次新建目录中的文件，原文件及已有目录保持。限制40MiB/40000行/20片，服务器单请求限制不变。

迁移 `a12c4b907e61` 增加ImportGroup，以及ImportBatch可空group_id/group_part。API只接收协议；ImportGroupService核对清单、范围、版本与撤销，仓储负责作用域查询。服务在用户锁下将相同清单和选项复用为原活动组；分片须匹配文件名、指纹、字节、行数、类型、渠道、身份、时区、导出时间。重试返回已有draft/preview/committed批次；撤销、清除或过期后可重传原片，组内每槽只有一个当前批次。映射沿用已提交片，修正仍经原预览和A1-1语义审阅。跨片相同业务键不同规范值阻止提交，相同值复用原业务投影并可恢复来源版本。

总量展示源记录、已提交片/行、组内唯一业务键、重叠行；不把源记录数当成订单数量。组未完整时，分析、运营、总览、商品质量、账单费用核对、订单账单核对和结算判断返回409 partial_coverage及下一步。产品成本来源跨渠道使用，故产品未完成组对同身份的订单渠道仍生效。组创建也是来源覆盖变化，递增店铺revision并使旧结果/审批失效；旧快照保留原值。

整组撤销经defer_commits顺序调用原单批撤销，包括原人工商品修改祖先保护；一次事务完成或全部回滚。独立来源保持有效，单片撤销使组重新部分覆盖。所有历史组可游标分页读取，API刷新可继续。导入组完成仅证明清单内分片已提交；全店/平台覆盖仍取决于卖家选择的原报表范围。

分析已有10000行读取上限，运营单分支10000行；商品质量和账单核对另有1000行限制。都保留超限拒绝，不截断后给完整结论。迁移在存在活动导入组时先拒绝降级，防止覆盖保护丢失。迁移升降级仅在3308隔离库验证，3307与3309未升级；用户启用新代码前需按维护说明备份并升级。验收见[r2-a1-2-acceptance](r2-a1-2-acceptance.md)。


本项目面向个人跨境卖家，使用 CSV/Excel 作为首版业务入口。完整需求见 [冻结稿](requirements/SoloOps-V1.0.md)，验收状态见 [功能矩阵](feature-matrix.md)。这是持续更新的工程说明，代码、测试与运行证据决定完成状态。

## 一、整体思路与迭代顺序

先建立可运行、可验证的最小纵向功能：账号与经营资料 → 文件导入与映射 → 确定性利润分析 → 受控问数 → Listing 草稿与审批 → 客服草稿 → 今日运营。每次交付均包含前后端、持久化、错误处理、测试与说明。

P0 的 23 个模块围绕四条 MVP 实现最小切片；P1/P2 保留完整清单，按实际授权逐步启用。界面只展示真实记录，初次使用显示空状态与下一步操作。

## 二、三层架构如何落地

```text
Vue 页面 → api 客户端 → FastAPI routes（接口层）
                         ↓
                      services（业务层）
                         ↓
                      repositories（数据访问层）→ MySQL
```

- 接口层：校验 HTTP 输入，读取当前身份，调用服务，返回稳定的响应模型；不计算业务金额、不拼 SQL。
- 业务层：执行权限、业务约束与事务决策。独立函数承载可重复的计算；服务组织一个用例涉及的持久化动作。
- 数据访问层：封装 SQLAlchemy 查询与写入，所有业务资源按拥有者过滤；数据库约束负责并发情况下的最终一致性保护。
- `schemas` 定义输入输出契约；`models` 描述持久化结构；`core` 放配置、时间、密码等共用能力。这些是三层的辅助模块。

选择模块化单体，进程内调用服务即可。先使用同步数据库访问配合 FastAPI 的同步路由线程池，让调用顺序、事务与调试容易理解。

### 身份与请求处理

本机 CLI 创建账号和恢复密码，不提供开放注册。密码至少 12 位，使用 Argon2；登录成功生成随机会话，数据库只存会话摘要。HttpOnly + SameSite Cookie 承载身份，CSRF Token 与来源白名单保护写入。密码恢复清除该账号全部会话。账号连续失败 5 次锁定 15 分钟，锁定状态落库；公开部署前还需入口级请求限流与 HTTPS。

浏览器通过 Vite 同源 `/api` 代理访问后端，CSRF Token 只存前端内存。HTTP 错误统一为 `error.code/message/request_id`；错误不返回原始密码、SQL 参数或堆栈。日志记录请求编号和异常类型，便于定位且减少泄露。

### 资料修改与并发

每份资料带 `version`。服务先锁当前用户及资料行，再比较客户端版本；版本过期返回 409，前端保留输入并提示刷新。创建店铺使用 `(owner_id, code)` 唯一约束，跨账号同名可以共存。同一次修改及其审计记录在一个事务中提交。

## 七、商品与订单导入切片

### 流程与职责

`api/routes/imports.py` 接受限长文件流并校验会话/CSRF；`services/import_parser.py` 负责有界解析，`import_catalog.py` 定义字段及别名建议，`import_validation.py` 做逐行确定性规范化。`services/imports.py` 组织预览、提交与撤销；`repositories/imports.py` 负责拥有者/店铺作用域、业务投影和版本查询。Vue 的 `ImportsView.vue` 组织步骤，`ImportMapping.vue` 与 `ImportRows.vue` 分别展示映射、源值和修正值。

上传建立有 24 小时有效期的草稿，未确认不会写入商品/订单行。界面允许选择报表类型、来源渠道、数据身份、时区和导出时间；字段映射可以修改或保存为个人模板。预览产生每行错误、警示和新增/更新/相同判断，所有错误修正后才能整批提交。更新已有记录需明确勾选覆盖确认。未知列名、无稳定行号、平台状态口径不一致等情况都需用户核对。

### 持久化与撤销算法

- `import_batches` 保存身份、店铺、文件指纹、映射、行数、币种、时间覆盖和状态；`import_rows` 保存选中字段的源值、修正值、规范化值及差异。
- `products` 与 `order_lines` 是当前有效业务投影，分别约束 `(shop_id, sku)` 与 `(shop_id, order_id, line_id)`；标识符大小写敏感。金额使用 `Numeric(18,4)`，服务使用 `Decimal`；历史 JSON 金额为规范十进制字符串。UTC 日期时间保留微秒。
- 导入提交按用户行锁串行化，并采用 MySQL 当前读，避免认证阶段已建立的 REPEATABLE READ 快照导致读到旧版本。预览记录店铺 `data_revision`；提交时发生数据变化则返回 409，要求重新预览。
- 每批确认至多生效一次；重复确认返回同一结果。重复文件按业务键比较，相同内容不增加订单行，但保留独立批次来源。相同数值不同小数格式视为相同。
- 撤销时标记批次不生效，再从**仍有效批次中按提交版本**为每个受影响业务键选最新记录；没有剩余版本才删除投影。这样先撤销 A 再撤销覆盖 A 的 B，也不会恢复已撤销 A。其他店铺和独立业务键保持有效。
- 生效/撤销使店铺数据版本递增，并在同一事务中使保存的分析与核对待办失效；清除批次按来源依赖清理对应快照和待办内容。具体持久化边界见第八节。

### 数据口径与安全边界

CSV 限 UTF-8，Excel 限单工作表 `.xlsx`；2 MiB、2000 数据行、64 列、每单元格 2000 字符。ZIP 解压内容最多 16 MiB/256 项，安装 defusedxml 并拒绝宏、外链、嵌入对象、公式与错误单元格。公式值不会执行，也不会采用缓存结果作为事实；错误定位后可用核对过的值修正。源行号对应 CSV 记录起始行或工作表行号。

所有内容按非可信文本展示，Vue 插值转义；错误报告的文本单元格采用 spreadsheet literal，CSV/Excel 模板只包含固定可信表头。上传不调用模型或外部工具。平台别名为候选，仅经过两种合成格式测试；整单收入、退款不能映射成行单价或行退款。状态采用明确枚举，取消/待支付/测试行提示不计入已支付销售。缺折扣、退款或成本保留未知，异币种显式展示；计算规则与缺口处理见第八节。

上传草稿暂存完整有界表格以便重新映射，过期后不可提交，并在后续导入访问时清理；提交时立即丢弃未映射列。撤销已提交批次保留来源供复核；清除会删源行与修正内容、清理相关旧值快照和文件名，并处理依赖的分析和核对待办，只保留必要状态与审计。主动清除入口也适用于过期草稿。长期审计期限和后台清理策略需用户确认，见 questions.md。

## 八、确定性已知毛利与受控问数

### 计算与接口

`api/routes/analytics.py → services/analytics.py → repositories/analytics.py` 负责范围验证、拥有者隔离和事务；`profit_calculation.py` 是无副作用计算核心。只读取当前有效投影；店铺、数据身份、币种、时区和带偏移起止时间均明确。按订单时间包含起点、不含终点，最长 366 天，超过 10000 行拒绝并提示缩小范围，不截断后冒充完整统计。

`paid/partially_refunded/refunded` 归入已支付来源，取消/未付款/测试行列明排除；数量是退款前的原购买数量。净销售额 = 数量 × 折扣前单价 − 行折扣 − 行退款。退款记入原订单时间窗口，缺退货数量不扣减购买件数、不恢复采购成本或库存。

当前商品采购成本用于历史订单是估算，未掌握成本生效日；界面提供成本源批次、导出/导入时间，二者不冒充成本生效时间。缺折扣、退款、成本、成本币种不一致或数据身份不同均保留未知；合计分别输出完整金额和可核对子集。毛利子集仅包含收入/成本同时已知的行，不能拿两个覆盖率不同的部分总额相减。Decimal 上下文精度 40，数据库保持 Numeric，JSON 以十进制字符串保存。毛利率显示保留两位，阈值判断使用未舍入乘积。

低毛利问题有可编辑的最低购买数量与毛利率上限；任一计入行不完整或同范围存在其他币种时暂停完整毛利筛选。销量前五只按明确的币种和身份范围内原购买数量排列，同量按 SKU 稳定排序。平台、广告、物流、税费等尚未归集，统一列出费用缺口，不生成精确净利润。

### 来源、保存和失效

`saved_analyses` 保存规范化范围、店铺来源版本、完成时间与快照；`analysis_sources` 显式关联订单和成本批次；`analysis_todos` 每个分析至多一个核对待办。相同拥有者、店铺、来源版本及口径的请求散列作为幂等键。保存时服务重新计算并校验用户看到的 `expected_revision`，不信任客户端传入金额。

导入提交/撤销在同一事务中将该店铺所有已有分析及待办标记为 `stale`。这是保守的店铺级失效：独立范围的旧快照保留，但需重算确认。清除批次仅清理显式依赖它的分析快照、来源关系和待办标题，状态为 `cleared`，保留 ID/范围/版本/时间及必要操作审计；独立结果与其他店铺内容保留。历史来源仍可读取已撤销而未清除的行；清除后返回 404。

所有这些操作使用用户→店铺→来源→派生记录的锁顺序及 MySQL 当前读。响应在事务提交前组装，避免提交后取待办锁又在后续操作获取用户锁的顺序反转。并发测试预先建立旧快照再同时保存/建待办，结果仍各一条。

### 可用交互与能力状态

`AnalyticsView.vue` 沿用工作台视觉，支持范围、三个受控问题、SKU 汇总、每页 20 行证据、按需展开原始值/修正值/规范化值、保存分析及创建核对待办。历史列表仅取最近 50 条摘要，单条展开再读取快照；可以按历史范围重算。窗口重新获得焦点或手动刷新时检查来源版本，历史结果显示失效，服务端在保存和建待办时再次校验。

问题入口只映射声明的三个问题或显式 intent 到只读计算服务，其他文本返回 `unsupported_question`，不会拼接 SQL、执行源码或把来源内容当指令。UI 和 API 标识 `local_rules`；真实模型适配、通用自然语言理解、模型预算和 Agent 技能选择尚待后续实现与凭据验证。MVP-04 目前是可用的确定性分析→来源→保存待办基础切片，不计完整 AI 闭环完成。

本轮测试全部为合成数据。真实用户报表、平台授权和模型凭据仍见 `questions.md`。

## 九、Listing 草稿与本地审批

### 分层、事实与生成器

`api/routes/listings.py` 负责有类型的 HTTP 输入和会话；`services/listings.py` 管理候选、版本、审批与事务；`repositories/listings.py` 封装拥有者/店铺范围的当前读、去重和来源清理。`ListingsView.vue` 组织商品选择与版本列表，`ListingReview.vue` 负责事实、差异、编辑和确认。沿用原有绿色工作台及手机布局，不引入组件依赖。

默认 `FactTemplateGenerator` 仅将商品名称和参数原文生成候选，输出身份 `local_template`。`ListingGenerator` 是可注入的类型接口，只接收名称/参数文本；测试用 `test_double` 检查虚构声明与生成失败。真实模型适配尚待实现，未来网络生成应放在数据库锁之外，并在写回时重新核对来源与基线。

`check_content` 采用保守的完整原文覆盖规则：标题保留完整商品名，可用固定分隔符连接完整参数行；描述每行须是完整参数行或完整商品名。支持选用、排序与省略，新增或改写文字保留为待审草稿但阻断批准。此检查不证明原始事实真实或平台合规，批准还要求用户逐项确认。缺参数明确提示，仅生成商品名；订单/成本/库存缺失不阻断此用例。生成器接触不到数据库与工具，来源中的指令作为普通文本保存并由 Vue 转义显示。

### 独立版本、并发与审批

`listing_versions` 保存序号、状态版本、来源状态、不可变内容快照、比较基线、生成方式与时间；`listing_sources` 保存快照依赖的全部导入批次。导入商品投影始终保留导入事实，批准只设定独立的本地 Listing 生效版本，外部状态固定为 `not_submitted`。

状态分两维：流程为 `draft / approved / rejected / superseded`；来源为 `current / stale / cleared`。批准、拒绝和替代不会改写候选文案；编辑生成新版本，历史拒绝记录保留。可以将来源仍有效的历史文案另存为新候选，再批准以恢复本地文本。每次显示店铺/SKU、旧值/新值、来源、R1 风险、本地作用域、0 外部费用、恢复方法及外部未提交状态。过期批准仍保留审批历史，页面明确提示需重新生成。

服务先持有用户与店铺锁，用当前读比较 `expected_source_row_id`、状态 `version` 与 `base_version_id`。相同来源/基线/生成器/失效阶段的生成请求及相同编辑请求散列去重，唯一约束兜底；重复批准仅返回已有结果。两个以相同旧版本为基线的候选竞争时，仅一个批准成功，另一个返回 409，需刷新后另存新版本。响应在 commit 前组装，提交后不再获取业务锁。审计保存动作、编号、来源覆盖阻断规则和时间，不存文案。

### 来源更新与清除

导入提交/撤销在同一事务比较候选所依赖的当前商品源行：该行不再是商品现值则永久标 `stale`，无关 SKU 与纯订单导入不失效。撤销覆盖批次恢复旧源行时，旧审批/草稿不会自动复活；失效阶段进入生成幂等键，允许重新建立可审核候选。

版本快照的依赖同时包含新文案来源、旧值比较来源和复制的历史内容来源。清除任一相关批次会清空整个快照、源行外键和依赖关系，保留无正文的序号、状态、时间和审计。即使清的是已撤销旧批次，后续版本保存的旧值也会清掉；其他 SKU 的独立结果保留。商品关联散列只用于持续编号和查询，不作为可展示事实。

### 本轮验证与限制

真实 MySQL 验证审批前零生效、原商品不被改写、拒绝与恢复、未覆盖文字阻断、生成失败不泄露细节、并发幂等/竞争、来源撤销与旧值清理、跨用户/店铺隔离、CSRF 和输入白名单。浏览器验证刷新持久化、查看源行、修改、确认、批准、拒绝、撤销失效与清除。四条 MVP 仍未完整完成：本轮交付本地版本/审批能力，真实 LLM、受控技能注册、统一任务、预算与熔断继续实施。

## 十、客服消息、政策证据与人工接管（2026-10-09）

### 入口与分层

`/support` 提供手工录入→源值/旧值预览→确认保存，也可在 `/imports` 导入客服 CSV/Excel。两种入口共用既有有界解析、映射、纠错、重复对比、覆盖确认与批次撤销/清除。消息正文上限 2000 字，与解析器一致；语言由用户标注 `en/zh/und`，未知语言保留原文并提示人工翻译。`examples/imports/messages-synthetic.csv` 仅含合成样例。

`CustomerMessage` 是当前投影，业务键为店铺+渠道+消息标识，UTC 微秒时间落库。API、`SupportService`、`SupportRepository` 分别负责契约、用例、查询；所有资源限定拥有者与店铺。页面支持消息检索、原始行、证据核验、建稿、编辑、转人工、存档和重新打开，外部状态固定 `not_submitted`。

### 证据与回复

消息中的订单号是待核验线索。仅列出同店铺、同数据身份、同来源渠道的订单，最多 100 行，超限拒绝而非截断。用户核验客户与订单关联后，生成请求提交所看到的全部源行 ID；服务在用户锁内当前读重新比较，变化返回 409。未确认候选不复制进草稿。快照只保存订单号/行号、SKU、订单及文件履约状态、源引用，不要求买家地址或邮箱。

政策保存编号、主题、文本、市场、渠道、语言、数据身份、出处、来源版本、人工核对状态与生效区间 `[from,until)`，日期须含时区。编辑另存新版本并立即取代旧版本；未来版本生效前不进入候选。标题/正文可检索；草稿按当前时间、消息范围和主题筛选。过期、未来、异店铺/渠道/语言/身份政策不能被伪造 ID 选入。多份同主题政策提示人工核对冲突。清除后可按原编号重新录入新版本，不恢复原引用。

`support_rules.py` 使用中英文关键词多标签匹配，保留物流、退款、取消、地址变更/拦截、争议、保修和一般 FAQ 等并存意图。`local_rules` 明示局限；未知语言/意图、敏感请求、缺政策、政策冲突或未知物流进入 `human_review`。已核对且无冲突的单一 FAQ 可引用完整政策原文。物流模板说明无法验证当前轨迹/送达日期，退款模板说明尚未确认退款。当前没有运单事实接入，CSV 中的 `fulfilled` 不作为实时物流证据。

### 并发与生命周期

草稿快照保存原消息、已核验订单、选用政策版本、多意图、接管原因、摘要和正文。人工修改标 `manual`，保留证据和接管原因。`draft/human_review/archived` 表示本地处理进度，存档不表示已发信或已执行售后操作。生成散列幂等，编辑/状态动作带版本；并发不同正文一个成功、一个 409，相同编辑无重复副作用。前端未保存正文时禁用切换、刷新和存档。

导入提交/撤销在同事务检查消息源行；来源被覆盖/撤销的草稿永久 `stale`，源行恢复后可新建稿，不复活旧草稿。订单数据变化保守失效该店铺已核验订单草稿，防止新增订单行漏检；无订单证据草稿保留。政策增修保守失效店铺已有草稿；服务访问时检查政策到期并落盘。响应在 commit 前组装。

`reply_sources` 关联消息及已核验订单批次，`reply_policies` 关联政策版本。清除任一引用来源会擦除整个草稿快照及源行引用，包括人工编辑正文；保留无正文编号、状态、时间和审计。旧政策清除不影响只引用新版本的草稿，独立消息草稿保留。审计存动作、编号、版本和意图标签，不存正文。

### 验证与限制

页面沿用绿色工作台，Vue 转义消息、政策和正文；源行可展开，时间明确业务时区。手机保留状态与意图标签。测试覆盖过期、冲突、越权、来源清除、并发和恶意文本，见 testing.md。真实模型、自动语言检测、实时运单、多轮会话、通道外发与售后执行仍待实现，MVP-03 不标完整完成。

## 十一、可选库存快照（2026-10-09）

`inventory` 是现有导入流程的第四类数据，继续使用相同文件边界、字段映射、预览纠错、覆盖确认、来源版本和撤销算法。字段为 SKU、已知可售数量、快照时间和卖家自设安全阈值；数量和阈值为 0—1000000000 的整数，空值不补零。未来快照拒绝导入；时间较现值更早的覆盖须显示警示并由用户确认。

## 十二、今日运营检查与本地待办（2026-10-09）

### 来源有效性与擦除

来源状态 `current / stale / cleared` 独立于处理状态。导入提交/撤销在同事务使店铺检查摘要失效，逐源行判断订单/消息/库存候选的当前投影是否变化；毛利因范围内新增行可能改变完整性，遇商品/订单变化保守失效，重跑相同证据后再核对。恢复旧源行不会自动复活待办来源，需实际再运行检查。库存结论和检查摘要在最早有效快照截止时失效，读取、审批前按服务端时间核对；过期批准被拒绝，历史可忽略。

清除任一依赖批次，擦除关联检查快照、待办快照、自由备注、截止时间和历史事件详情，并删除来源关系，保留无正文的编号、规则类型、状态、版本和必要审计。旧成本批次已被覆盖仍能清理引用它的历史结论；独立消息/库存事项保留。用户→店铺→来源→派生的锁序保持一致，响应在 commit 前组装。前端窗口 focus/刷新再次核对；有未保存备注时阻止切换/刷新，操作请求进行中阻止切换对象。

## 十四、独立新品利润计算器（2026-10-09）

### 单件模型与财务口径

`api/routes/profit.py → services/profit.py → repositories/profit.py` 管理店铺内方案；`profit_rules.py` 是独立的确定性计算。无需订单或商品导入。每次试算共享一个结算币种，包含 1—5 个不同名称的方案。售价和采购价必须明确；九类费用为头程、尾程、平台、仓储、包装、广告、退款损失、税费及其他分摊。每项是固定单件金额或售价百分比，空值表示未知、零表示显式零假设；任何已填费用必须提供依据，售价/采购成本也有依据字段。

金额以十进制字符串经 Pydantic 进入 Decimal，限制非负、最多四位小数且不超过一亿元；单项费率不超过 100%，总费率可以超过并明确显示无法保本。计算使用局部 40 位精度：采购毛利为售价减采购成本；已知费用后余额再扣已填固定项及售价比例费用；余额率以未舍入余额计算，HALF_UP 保留四位小数，零售价时未知。输出金额保持原值，前端不转二进制浮点。费用不全时仅给已知余额并逐项列缺口。

只有九类费用均明确且总售价费率小于 100% 时，保本价按 `(采购成本 + 固定费用) / (1 − 比例)` 得出，再向上取整到 JPY 的 1 或其余支持币种的 0.01，避免建议价因四舍五入仍亏损。这是手填模型的覆盖价，未归集费用、税制、退款概率、销量和真实净利润仍不能据此确定。当前每类费用一个固定项或一个售价比例，阶梯费率、佣金最低收费及多币种换汇待扩展。

每个方案固定展示售价 −10%、原方案、售价 +10%、采购成本 +10% 四组单变量敏感性。比例费随售价重算，固定费不变，未知项继续未知。多物流/价格方案由用户另填或复制后修改，所有输入及依据可展开核对。

### 消耗、幂等与恢复边界

沿用用户→店铺锁序与 `FOR UPDATE` 当前读。授权校验、业务保存、额度消耗、依赖登记与步骤完成位于同一事务/savepoint；任意失败一并回滚。两个已建立旧 RR 快照的执行争用最后一次额度只有一个成功。每次成功保存消耗 1 次，包括复用候选；HTTP 回放或同一执行 UUID 不重复扣减。新增可选输入字段为空时不进入请求摘要，保持旧无授权任务的 UUID 回放兼容性。

来源清除沿用 Agent/Operations 的依赖擦除；授权仅留范围、摘要和无正文消耗审计。授权创建 UUID、撤销与候选撤回均支持安全回放。`origin_execution_id` 是经拥有者/店铺校验的溯源 ID，避免与 Agent 的授权外键形成数据库循环依赖；业务执行与消耗关系有外键和唯一约束。

## 二十、模型驱动的经营问数与证据解释（2026-10-09）

### 分层与业务闭环

复用 `api/routes/agent.py → services/agent.py → repositories/agent.py` 的持久执行，新增 `question` 流程：`question_plan → metrics → explain_analysis → analysis_todo（需要时等待审批）→ verify`。模型选择 summary / sales / low_margin / unsupported；范围、日期、币种和阈值由卖家表单固定。`metrics` 仍调用 AnalyticsService 和 Decimal 计算，订单统计覆盖全店所选身份，渠道只用于绑定本次经营规则。八项受控技能的元数据与工具声明经过同一白名单校验。

`analysis_explanation.py` 从已验证 AnalysisResult 生成有界事实目录：范围覆盖、汇总、费用缺口及最多 20 项候选或汇总 SKU。供应商只收到匿名 item 编号及数值，不收到订单号、SKU 文本、文件名、原始行或客服正文。用户的问题原文会发送，页面单独说明。完整本地统计与引用仍保存在 metrics 步骤内，原始行可以通过既有来源 API 查阅。

模型生成的业务内容是证据顺序、核对建议及 finish / offer_todo 分支。输出仅允许受控事实和建议 ID；重复、越界、额外字段或无建议却要求待办均阻断。覆盖结论与费用缺口强制保留，金额与事实句由本地已验证数据渲染。核对建议明确属于待验证事项，不能当作已确认因果。模型既不能改数，也不能通过文本选择新工具或外部写入。

需要核对时，用户审阅后批准 `analysis_todo` 技能，调用现有保存分析与创建待办服务；外层 savepoint/defer_commits 使统计快照、来源、待办、步骤与审计原子提交。已有相同来源和口径复用分析与待办，已完成进度不重置。verify 回读分析状态和待办 ID，页面深链打开确切店铺及分析，复用完成/重开入口。解释持久于执行步骤，审批完成后仍能回看；来源清除时与原始统计一起擦除。

### 模型协议、成本与在途状态

`OpenAIResponsesModel.generate` 使用固定 Responses HTTPS 端点、store=false、text.format 的严格 JSON schema、无工具、禁止代理和重定向。请求体最多 60000 bytes，输出上限 768 tokens，响应最多 200000 bytes。默认关闭，启用、凭据、模型和输入/输出美元费率均须配置；页面展示供应商、模型及配置费率。每个问题另有目标文本与匿名指标两项明确同意，改变范围/目标/预算会清空同意。

正常流程含两次模型请求。每次沿用保守 UTF-8 包络和输出上限预留 Decimal 费用，调用前持久化租约并释放数据库锁；每次都检查剩余预算、步骤/耗时、规则版本与来源。第二次费用不足时暂停并保留已完成统计，用户可提高总预算恢复。

新协议区分内容与费用：usage 有效但拒答、未完成、JSON/事实 ID 错误时保留已知费用并阻断输出；无 usage、超时、重定向或超限保留未知预留，不自动重发。返回后重新取锁核对版本/租约/来源；暂停、取消、规则或来源变化后的结果丢弃，费用照记。清除期间返回只处理费用/状态，不恢复输入和解释。暂停的已知回包丢弃后，显式恢复可重新请求并在原总预算下计费，页面已说明；未知费用不可恢复。实际供应商账单需另核对。

### 页面与验证范围

AgentView 新增 AI 经营问数，AnalyticsView 提供入口。AnalysisNarrative 展示模型组合的证据、缺口、待验证建议及完整本地筛选范围；事实原始行、公式和当前成本估算边界继续可查。AgentRunReview 显示审批和费用，保存后链接确切分析；商品/客服结果深链同时携带原对象 ID。切换店铺和详情采用请求序号丢弃旧回包。

测试以 HTTP MockTransport 或进程内模型替身验证。浏览器替身仅注册于强制 `_test` 库的 serve_e2e，且限定 `question-e2e-` 合成店铺；生产工厂不注册，替身无网络路径。完整后端、桌面/手机浏览器和组件验证见 testing 第十五迭代。本切片无需新表或迁移。实际模型理解质量和供应商费用仍待用户配置与授权，完整 P0 的其他模型业务切片继续实施。

模型步骤输入同时保存本次公开配置快照（供应商、模型名、费率），用于历史费用解释，不包含凭据。`AnalyticsService.save_and_create_todo` 是内置技能实际调用的组合业务入口，嵌套 defer_commits 支持独立调用与外层执行事务。

## 二十一、模型 Listing 候选与独立本地审批（2026-10-09）

## 二十三、客服模型候选与人工接管（2026-10-09）

### 分层、事实与权限

`support_model` 流程为 `support_context → compose_support → support_candidate（等待审批）→ verify`。新增两项固定技能，注册表共十一项。接口继续调用 AgentService；客服准备与保存通过 SupportService，数据库操作复用既有 repository 和 JSON 快照，无新表或迁移。

`support_composition.py` 构造三个固定事实编号（人工核验关联、当前物流缺口、业务权限边界）和最多十份卖家选择的政策编号。模型识别八类意图、排列全部事实编号、选择政策、提出 offer_draft / handoff；重复、越界、遗漏事实或额外正文/工具字段阻断。消息意图与本地规则取并集，本地 unknown 和敏感条件保留。模型可增加语义识别出的诉求，不能删除本地识别结果或推定身份。

回复由本地中英文模板和完整、已确认的单份 FAQ 原文组成。普通 FAQ 需要明确意图、唯一适用且已核对政策；退款、物流、争议、订单变更、保修、未识别语言、缺政策或冲突均保留人工接管。即使模型选择 offer_draft，本地条件也能将其降为人工处理候选。政策池沿用本地意图主题和店铺/市场/渠道/身份/语言/有效期筛选，语义检索、自动语言检测与多轮仍为后续范围。规则未知时需要人工核对。

### 发送范围与来源一致性

Agent 页面加载消息原文和适用政策，卖家逐份勾选政策，订单关联须显式核验全部当前订单行。目标授权与客服数据授权分别记录；客服上下文绑定消息源行、政策版本 ID、已核验订单源行集合。消息、政策、订单核验、范围或预算改变会清空同意，刷新中和迟到请求不会使旧资料再次可选。

一次模型请求发送目标、消息正文及标注语言、选中政策主题/全文/来源确认布尔值、人工关联状态和固定规则缺口。结构化订单号、订单行、SKU、文件名、政策出处不在投影内；消息/目标/政策原文本身若包含个人信息或订单号，会随正文发送，页面明确提示并要求审阅。开发测试从不调用本机已配置的真实模型。

`_current_support` 在网络前、回包后和审批加载时重建准备快照；`save_candidate` 重新验证其摘要。当前来源、订单行集合、政策适用性、冲突、有效期和规则变化均会使旧预览失效。最早政策截止时间写入 Agent 有效期。准备服务在 Agent 事务内使用 defer_commits，模型请求通过已有持久租约释放数据库锁后执行。取消或清除不采纳回包，已知 usage 仍记费，费用未知时保留预留并禁止自动重发。

### 保存、回读与页面

审批后调用 `SupportService.save_candidate`，去重键包含准备快照摘要、选择、来源、供应商及失效世代。重复候选复用既有草稿，人工编辑和存档状态保留。ReplyDraft、消息/已核验订单/全部已发送政策依赖、审计和 Agent 步骤同事务保存；失败回滚。模型未选择的一份已发送政策也保留依赖，清除后擦除关联执行与草稿正文。

`SupportModelContext.vue` 展示发送范围、源行和政策全文，`SupportCandidatePreview.vue` 展示客户原文、拟议回复、全部诉求、接管原因与引用。桌面双栏，手机单栏。审批后回读草稿 ID，深链打开准确客服记录，可编辑/转人工/存档。页面和持久记录明确外部未提交，实际退款和客户联系仍由独立权限门禁决定。

## 二十四、运营模型概览与候选审批（2026-10-09）

### 分层与受控事实

新增 `daily_model`：`data_check → explain_operations → propose_tasks（审批）→ verify`，复用现有十一项技能与 OperationsService。`operation_explanation.py` 只接收分支编号和核对建议编号，允许安排顺序；全部九个检查分支、四类候选数量、原始缺失原因及各类核对建议均由本地规则保留。存在候选必经审批，无候选则保存解释并结束，不把未检查解释为经营正常。具体异常、阈值、金额、来源仍由 operation_checks 和 Decimal 计算决定。

模型只收到目标原文、范围（时间/时区/币种/身份/渠道/阈值）、分支名称/状态/行数、四类候选计数与固定核对建议。分支详细原因、对象标识、SKU、订单号、文件名、消息正文和具体数值不发送；目标正文由用户核对。固定建议仅为待核事项，没有已确认因果或新业务权限。两种供应商继续复用既有无工具协议、预算预留、usage 计费及未知不重试。

## 三十一、人工收费类别映射与调整历史（2026-10-09）

预览复用 `StatementService.reconcile` 的同店铺半开时间窗和每侧 1000 行/笔上限。`defer_commits` 保持用户→店铺锁直到外层事务结束；规则、账单及费用均使用锁定当前读与 populate_existing。服务模拟当前规则替换后逐行计算 before/after，返回原规则、拟保存内容、分类变化、原始来源入口、来源版本和读取时刻。新规则在预览中使用临时编号 0，不持久化任何账单应用结果。

预览散列绑定匹配契约、完整输入/窗口、店铺来源版本、当前账单与费用版本、所有有效规则版本/内容，排除读取时刻。明确确认后，服务在同锁事务重算并比较散列，任一相关变化要求重新预览；来源覆盖后撤销恢复仍有新 data_revision，旧预览不能重新使用。保存 UUID 绑定动作、店铺、目标、版本、预览散列与所有输入；重放返回当前规则，不重复生成版本。规则、修订历史与审计原子提交，审计失败整体回滚。

### 当前分类与事实边界

`fee_mapping.map_fees` 仅处理当前 fee 账单行。完整收费名未命中为 unmapped；重复凭据或规则为 ambiguous；匹配人工费用币种不同为 currency_mismatch；规则类别与一对一人工费用类别不同为 category_conflict；其余命中为 mapped，仍标业务待核。重复/异币种保持类别待核，类别冲突展示拟分类及规则版本，金额差异仍由既有六类比较清单独立表达。页面可筛选分类状态、回读原行和查看规则编号/版本；金额与原账单、人工费用均保持原值。

## 三十二、人工核对结论与历史依据（2026-10-09）

## 三十四、订单销售与退款待核清单（2026-10-09）
