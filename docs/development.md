# SoloOps 开发文档

本项目面向个人跨境卖家，使用 CSV/Excel 作为首版业务入口。完整需求见 [冻结稿](requirements/SoloOps-V1.0.md)，验收状态见 [功能矩阵](feature-matrix.md)。这是持续更新的工程说明，代码、测试与运行证据决定完成状态。

## 一、整体思路与迭代顺序

先建立可运行、可验证的最小纵向功能：账号与经营资料 → 文件导入与映射 → 确定性利润分析 → 受控问数 → Listing 草稿与审批 → 客服草稿 → 今日运营。每次交付均包含前后端、持久化、错误处理、测试与说明。

P0 的 23 个模块围绕四条 MVP 实现最小切片；P1/P2 保留完整清单，按实际授权逐步启用。界面只展示真实记录，初次使用显示空状态与下一步操作。

## 二、三层架构如何落地

```text
Vue 页面 → api 客户端 → FastAPI routes（接口层）
                         ↓
                      services（业务层）
                         ↓
                      repositories（数据访问层）→ MySQL
```

- 接口层：校验 HTTP 输入，读取当前身份，调用服务，返回稳定的响应模型；不计算业务金额、不拼 SQL。
- 业务层：执行权限、业务约束与事务决策。独立函数承载可重复的计算；服务组织一个用例涉及的持久化动作。
- 数据访问层：封装 SQLAlchemy 查询与写入，所有业务资源按拥有者过滤；数据库约束负责并发情况下的最终一致性保护。
- `schemas` 定义输入输出契约；`models` 描述持久化结构；`core` 放配置、时间、密码等共用能力。这些是三层的辅助模块。

选择模块化单体，进程内调用服务即可。先使用同步数据库访问配合 FastAPI 的同步路由线程池，让调用顺序、事务与调试容易理解。

## 五、当前实现与运行证据

已实现身份与经营资料、四类文件导入、确定性分析、跨店总览与经营摘要、Listing 本地审批、客服草稿与政策证据、今日运营与受控执行、利润试算、经营规则/内部预授权及 R2 测试外发本地路径。当前实现和证据见下方章节与[测试记录](testing.md)；四条 MVP 的模型内容生成、统一任务驾驶舱及真实外部证据继续实施。

### 身份与请求处理

本机 CLI 创建账号和恢复密码，不提供开放注册。密码至少 12 位，使用 Argon2；登录成功生成随机会话，数据库只存会话摘要。HttpOnly + SameSite Cookie 承载身份，CSRF Token 与来源白名单保护写入。密码恢复清除该账号全部会话。账号连续失败 5 次锁定 15 分钟，锁定状态落库；公开部署前还需入口级请求限流与 HTTPS。

浏览器通过 Vite 同源 `/api` 代理访问后端，CSRF Token 只存前端内存。HTTP 错误统一为 `error.code/message/request_id`；错误不返回原始密码、SQL 参数或堆栈。日志记录请求编号和异常类型，便于定位且减少泄露。

### 资料修改与并发

每份资料带 `version`。服务先锁当前用户及资料行，再比较客户端版本；版本过期返回 409，前端保留输入并提示刷新。创建店铺使用 `(owner_id, code)` 唯一约束，跨账号同名可以共存。同一次修改及其审计记录在一个事务中提交。

### 进一步的问题与处理

| 问题 | 解决 | 证据 |
|---|---|---|
| 新脚手架 lint 辅助依赖带入已知 `braces` 风险 | 用 ESLint/TypeScript ESLint 基础配置完成同样检查，精简工具依赖 | npm audit 0 漏洞，lint/build 通过 |

| 测试可能误清真实数据 | 独立 MySQL 服务与 `_test` 数据库名防护 | 测试启动前校验，日常业务库独立 |

## 七、商品与订单导入切片

### 流程与职责

`api/routes/imports.py` 接受限长文件流并校验会话/CSRF；`services/import_parser.py` 负责有界解析，`import_catalog.py` 定义字段及别名建议，`import_validation.py` 做逐行确定性规范化。`services/imports.py` 组织预览、提交与撤销；`repositories/imports.py` 负责拥有者/店铺作用域、业务投影和版本查询。Vue 的 `ImportsView.vue` 组织步骤，`ImportMapping.vue` 与 `ImportRows.vue` 分别展示映射、源值和修正值。

上传建立有 24 小时有效期的草稿，未确认不会写入商品/订单行。界面允许选择报表类型、来源渠道、数据身份、时区和导出时间；字段映射可以修改或保存为个人模板。预览产生每行错误、警示和新增/更新/相同判断，所有错误修正后才能整批提交。更新已有记录需明确勾选覆盖确认。未知列名、无稳定行号、平台状态口径不一致等情况都需用户核对。

### 持久化与撤销算法

- `import_batches` 保存身份、店铺、文件指纹、映射、行数、币种、时间覆盖和状态；`import_rows` 保存选中字段的源值、修正值、规范化值及差异。
- `products` 与 `order_lines` 是当前有效业务投影，分别约束 `(shop_id, sku)` 与 `(shop_id, order_id, line_id)`；标识符大小写敏感。金额使用 `Numeric(18,4)`，服务使用 `Decimal`；历史 JSON 金额为规范十进制字符串。UTC 日期时间保留微秒。
- 导入提交按用户行锁串行化，并采用 MySQL 当前读，避免认证阶段已建立的 REPEATABLE READ 快照导致读到旧版本。预览记录店铺 `data_revision`；提交时发生数据变化则返回 409，要求重新预览。
- 每批确认至多生效一次；重复确认返回同一结果。重复文件按业务键比较，相同内容不增加订单行，但保留独立批次来源。相同数值不同小数格式视为相同。
- 撤销时标记批次不生效，再从**仍有效批次中按提交版本**为每个受影响业务键选最新记录；没有剩余版本才删除投影。这样先撤销 A 再撤销覆盖 A 的 B，也不会恢复已撤销 A。其他店铺和独立业务键保持有效。
- 生效/撤销使店铺数据版本递增，并在同一事务中使保存的分析与核对待办失效；清除批次按来源依赖清理对应快照和待办内容。具体持久化边界见第八节。

### 数据口径与安全边界

CSV 限 UTF-8，Excel 限单工作表 `.xlsx`；2 MiB、2000 数据行、64 列、每单元格 2000 字符。ZIP 解压内容最多 16 MiB/256 项，安装 defusedxml 并拒绝宏、外链、嵌入对象、公式与错误单元格。公式值不会执行，也不会采用缓存结果作为事实；错误定位后可用核对过的值修正。源行号对应 CSV 记录起始行或工作表行号。

所有内容按非可信文本展示，Vue 插值转义；错误报告的文本单元格采用 spreadsheet literal，CSV/Excel 模板只包含固定可信表头。上传不调用模型或外部工具。平台别名为候选，仅经过两种合成格式测试；整单收入、退款不能映射成行单价或行退款。状态采用明确枚举，取消/待支付/测试行提示不计入已支付销售。缺折扣、退款或成本保留未知，异币种显式展示；计算规则与缺口处理见第八节。

上传草稿暂存完整有界表格以便重新映射，过期后不可提交，并在后续导入访问时清理；提交时立即丢弃未映射列。撤销已提交批次保留来源供复核；清除会删源行与修正内容、清理相关旧值快照和文件名，并处理依赖的分析和核对待办，只保留必要状态与审计。主动清除入口也适用于过期草稿。长期审计期限和后台清理策略需用户确认，见 questions.md。

## 八、确定性已知毛利与受控问数

### 计算与接口

`api/routes/analytics.py → services/analytics.py → repositories/analytics.py` 负责范围验证、拥有者隔离和事务；`profit_calculation.py` 是无副作用计算核心。只读取当前有效投影；店铺、数据身份、币种、时区和带偏移起止时间均明确。按订单时间包含起点、不含终点，最长 366 天，超过 10000 行拒绝并提示缩小范围，不截断后冒充完整统计。

`paid/partially_refunded/refunded` 归入已支付来源，取消/未付款/测试行列明排除；数量是退款前的原购买数量。净销售额 = 数量 × 折扣前单价 − 行折扣 − 行退款。退款记入原订单时间窗口，缺退货数量不扣减购买件数、不恢复采购成本或库存。

当前商品采购成本用于历史订单是估算，未掌握成本生效日；界面提供成本源批次、导出/导入时间，二者不冒充成本生效时间。缺折扣、退款、成本、成本币种不一致或数据身份不同均保留未知；合计分别输出完整金额和可核对子集。毛利子集仅包含收入/成本同时已知的行，不能拿两个覆盖率不同的部分总额相减。Decimal 上下文精度 40，数据库保持 Numeric，JSON 以十进制字符串保存。毛利率显示保留两位，阈值判断使用未舍入乘积。

低毛利问题有可编辑的最低购买数量与毛利率上限；任一计入行不完整或同范围存在其他币种时暂停完整毛利筛选。销量前五只按明确的币种和身份范围内原购买数量排列，同量按 SKU 稳定排序。平台、广告、物流、税费等尚未归集，统一列出费用缺口，不生成精确净利润。

### 来源、保存和失效

`saved_analyses` 保存规范化范围、店铺来源版本、完成时间与快照；`analysis_sources` 显式关联订单和成本批次；`analysis_todos` 每个分析至多一个核对待办。相同拥有者、店铺、来源版本及口径的请求散列作为幂等键。保存时服务重新计算并校验用户看到的 `expected_revision`，不信任客户端传入金额。

导入提交/撤销在同一事务中将该店铺所有已有分析及待办标记为 `stale`。这是保守的店铺级失效：独立范围的旧快照保留，但需重算确认。清除批次仅清理显式依赖它的分析快照、来源关系和待办标题，状态为 `cleared`，保留 ID/范围/版本/时间及必要操作审计；独立结果与其他店铺内容保留。历史来源仍可读取已撤销而未清除的行；清除后返回 404。

所有这些操作使用用户→店铺→来源→派生记录的锁顺序及 MySQL 当前读。响应在事务提交前组装，避免提交后取待办锁又在后续操作获取用户锁的顺序反转。并发测试预先建立旧快照再同时保存/建待办，结果仍各一条。

### 可用交互与能力状态

`AnalyticsView.vue` 沿用工作台视觉，支持范围、三个受控问题、SKU 汇总、每页 20 行证据、按需展开原始值/修正值/规范化值、保存分析及创建核对待办。历史列表仅取最近 50 条摘要，单条展开再读取快照；可以按历史范围重算。窗口重新获得焦点或手动刷新时检查来源版本，历史结果显示失效，服务端在保存和建待办时再次校验。

问题入口只映射声明的三个问题或显式 intent 到只读计算服务，其他文本返回 `unsupported_question`，不会拼接 SQL、执行源码或把来源内容当指令。UI 和 API 标识 `local_rules`；真实模型适配、通用自然语言理解、模型预算和 Agent 技能选择尚待后续实现与凭据验证。MVP-04 目前是可用的确定性分析→来源→保存待办基础切片，不计完整 AI 闭环完成。

本轮测试全部为合成数据。真实用户报表、平台授权和模型凭据仍见 `questions.md`。

## 九、Listing 草稿与本地审批

### 分层、事实与生成器

`api/routes/listings.py` 负责有类型的 HTTP 输入和会话；`services/listings.py` 管理候选、版本、审批与事务；`repositories/listings.py` 封装拥有者/店铺范围的当前读、去重和来源清理。`ListingsView.vue` 组织商品选择与版本列表，`ListingReview.vue` 负责事实、差异、编辑和确认。沿用原有绿色工作台及手机布局，不引入组件依赖。

默认 `FactTemplateGenerator` 仅将商品名称和参数原文生成候选，输出身份 `local_template`。`ListingGenerator` 是可注入的类型接口，只接收名称/参数文本；测试用 `test_double` 检查虚构声明与生成失败。真实模型适配尚待实现，未来网络生成应放在数据库锁之外，并在写回时重新核对来源与基线。

`check_content` 采用保守的完整原文覆盖规则：标题保留完整商品名，可用固定分隔符连接完整参数行；描述每行须是完整参数行或完整商品名。支持选用、排序与省略，新增或改写文字保留为待审草稿但阻断批准。此检查不证明原始事实真实或平台合规，批准还要求用户逐项确认。缺参数明确提示，仅生成商品名；订单/成本/库存缺失不阻断此用例。生成器接触不到数据库与工具，来源中的指令作为普通文本保存并由 Vue 转义显示。

### 独立版本、并发与审批

`listing_versions` 保存序号、状态版本、来源状态、不可变内容快照、比较基线、生成方式与时间；`listing_sources` 保存快照依赖的全部导入批次。导入商品投影始终保留导入事实，批准只设定独立的本地 Listing 生效版本，外部状态固定为 `not_submitted`。

状态分两维：流程为 `draft / approved / rejected / superseded`；来源为 `current / stale / cleared`。批准、拒绝和替代不会改写候选文案；编辑生成新版本，历史拒绝记录保留。可以将来源仍有效的历史文案另存为新候选，再批准以恢复本地文本。每次显示店铺/SKU、旧值/新值、来源、R1 风险、本地作用域、0 外部费用、恢复方法及外部未提交状态。过期批准仍保留审批历史，页面明确提示需重新生成。

服务先持有用户与店铺锁，用当前读比较 `expected_source_row_id`、状态 `version` 与 `base_version_id`。相同来源/基线/生成器/失效阶段的生成请求及相同编辑请求散列去重，唯一约束兜底；重复批准仅返回已有结果。两个以相同旧版本为基线的候选竞争时，仅一个批准成功，另一个返回 409，需刷新后另存新版本。响应在 commit 前组装，提交后不再获取业务锁。审计保存动作、编号、来源覆盖阻断规则和时间，不存文案。

### 来源更新与清除

导入提交/撤销在同一事务比较候选所依赖的当前商品源行：该行不再是商品现值则永久标 `stale`，无关 SKU 与纯订单导入不失效。撤销覆盖批次恢复旧源行时，旧审批/草稿不会自动复活；失效阶段进入生成幂等键，允许重新建立可审核候选。

版本快照的依赖同时包含新文案来源、旧值比较来源和复制的历史内容来源。清除任一相关批次会清空整个快照、源行外键和依赖关系，保留无正文的序号、状态、时间和审计。即使清的是已撤销旧批次，后续版本保存的旧值也会清掉；其他 SKU 的独立结果保留。商品关联散列只用于持续编号和查询，不作为可展示事实。

### 并发与生命周期

## 十四、独立新品利润计算器（2026-10-09）

### 单件模型与财务口径

`api/routes/profit.py → services/profit.py → repositories/profit.py` 管理店铺内方案；`profit_rules.py` 是独立的确定性计算。无需订单或商品导入。每次试算共享一个结算币种，包含 1—5 个不同名称的方案。售价和采购价必须明确；九类费用为头程、尾程、平台、仓储、包装、广告、退款损失、税费及其他分摊。每项是固定单件金额或售价百分比，空值表示未知、零表示显式零假设；任何已填费用必须提供依据，售价/采购成本也有依据字段。

金额以十进制字符串经 Pydantic 进入 Decimal，限制非负、最多四位小数且不超过一亿元；单项费率不超过 100%，总费率可以超过并明确显示无法保本。计算使用局部 40 位精度：采购毛利为售价减采购成本；已知费用后余额再扣已填固定项及售价比例费用；余额率以未舍入余额计算，HALF_UP 保留四位小数，零售价时未知。输出金额保持原值，前端不转二进制浮点。费用不全时仅给已知余额并逐项列缺口。

只有九类费用均明确且总售价费率小于 100% 时，保本价按 `(采购成本 + 固定费用) / (1 − 比例)` 得出，再向上取整到 JPY 的 1 或其余支持币种的 0.01，避免建议价因四舍五入仍亏损。这是手填模型的覆盖价，未归集费用、税制、退款概率、销量和真实净利润仍不能据此确定。当前每类费用一个固定项或一个售价比例，阶梯费率、佣金最低收费及多币种换汇待扩展。

每个方案固定展示售价 −10%、原方案、售价 +10%、采购成本 +10% 四组单变量敏感性。比例费随售价重算，固定费不变，未知项继续未知。多物流/价格方案由用户另填或复制后修改，所有输入及依据可展开核对。

## 十八、跨店经营总览与日周月摘要（2026-10-09）

### 口径与业务边界

`api/routes/overview.py → services/overview.py / overview_calculation.py → repositories/overview.py` 提供跨店查询与持久摘要，复用现有 AnalyticsRepository 和 Decimal 订单计算。`/overview` 沿用现有绿系设计，平台/市场筛选最终落实为明确店铺 ID 集合；市场是登记经营市场，不代表买家收件国家。每次最多 20 家店铺，所有来源读取和计算合计最多 10000 行，超限整体拒绝。商品成本、订单、库存、消息均经 owner/shop/data_identity 条件查询；商品成本身份不匹配仍沿用既有未知门禁。

日期输入按 IANA 时区的当地零点分别转 UTC，范围含起点不含终点。默认比较此前同样日历天数，也支持显式自选对比区间。前日、近七个完整日、近三十个完整日生成日报/七日周报/三十日月报，自选窗口生成区间摘要。夏令时开始的一天可以是 23 小时，不能简单减固定 UTC 24 小时。不存在的当地零点拒绝，日历与换算后 UTC 窗口均限制不超过 366 天，超限返回可读 422；自选两个窗口允许不同长度，界面同时显示日期，不作按日归一化。

按店铺和币种独立计算，再对同币种的已覆盖店铺加总。销售沿用数量×单价−行折扣−行退款；退款归原订单日期。订单在每店每币种内去重，跨币种订单不能把分组计数再加总。完整值与已知子集分别展示，空范围不能证明零经营活动。差额仅在两期金额完整时产生；变化率还要求对比基数为正。Decimal 使用 40 位局部精度，前端显示金额字符串；派生快照 JSON 保存十进制字符串，原始金额仍为 Numeric。

采购成本使用当前商品记录，低毛利筛选按未舍入值及显式阈值判断；真实历史成本、净利润、营销数据缺失继续标未知。热销按原购买量排列，不推断净退货数量。订单未履约/部分履约按当前文件状态给出来源，状态缺失时不宣称完整待发货数。

库存为生成当时当前投影，按本页独立时效（默认 24 小时）逐渠道核验；过期/未来快照未知，全部未知时低库存数也未知。消息按本期发送时间筛选，回复状态未知。最近 50 条未结待办只记录当时 ID/类型/处理状态，需打开工作台重新核验；本页不创建运营候选。完整来源列表包括两期订单、实际引用的成本、当前库存与区间消息，可进入已有受权原始行 API，查看批次、导出/导入时间、原始值及修正值。导出截至未知不会用导入时间替代。

### 持久化、一致性与清除

迁移 `728544d1186c` 新增 overview_reports、overview_shops、overview_sources。统一用户锁之后按店铺 ID 升序取锁，以 FOR UPDATE + populate_existing 当前读计算，避免认证已建立的 RR 快照读取旧来源。保存请求只提交范围、期望来源版本和 UUID；服务端重算，版本不符返回 409，正文与审计同事务保存。UUID 绑定规范化范围和期望版本，相同请求回读原报告，换范围复用拒绝；清除后也不会复活正文。

导入提交/撤销使相关店铺报告保守 stale；保存结果保持当时数值，不静默按新数据改算。库存到期及未来快照的生效点形成下一核验点，读取到期报告时标 stale。有效期使用 MySQL DATETIME(6)：测试揭示默认 DATETIME 对小数秒舍入可能延后失效，已修正并验证精确边界。清批次时沿 OverviewSource 清除所有依赖报告的整个快照与来源关系，保留 ID、范围、状态和审计；其他独立报告不受正文清除影响。卖家也可主动明确确认清除摘要，重复清除幂等。

### 页面与验证

表单支持平台/市场/店铺、日期快捷项与自选对比、身份和币种筛选。生成后收起表单，按币种显示主金额和缺口，逐店查看公式、热销/低毛利、当前快照、消息与源行；可保存、游标分页历史、刷新状态和清除。切换输入隐藏旧结果，来源组件丢弃迟到的前份报告数据及错误；失效的未保存预览在刷新时隐藏。窗口聚焦时刷新来源状态，服务端保存仍做最终校验。

后端覆盖多店/多币种/退款/状态/日期边界、空数据/身份隔离、并发旧快照/幂等/审计失败回滚、库存到期、依赖清除、范围上限和历史分页。前端覆盖迟到来源响应；浏览器覆盖真实两店来源下钻、保存回读、撤销/清除和手机空数据。截图实际检查，测试使用合成数据。运行结果见 testing.md。本功能无模型或真实外发调用，统一驾驶舱和四条完整 AI MVP 继续开发。

## 十九、统一任务、草稿与审批驾驶舱（2026-10-09）

### 读取模型与范围

`api/routes/workbench.py → services/workbench.py → repositories/workbench.py` 为首页提供统一读取接口。十种既有对象包括运营待办、Agent 执行、Listing 版本、客服草稿、分析核对待办、运营检查、单店分析、跨店摘要、R1 预授权和 R2 邮件。每个 SQL 分支独立约束拥有者；店铺选择先校验归属。跨店摘要用关联表 EXISTS 筛选，避免按店铺关联而重复计数。首页只返回有界元数据、记录 ID、固定内部链接及简短摘要，不保存另一份正文或审批状态。

按店铺、数据身份、来源渠道和事项类型筛选。单店分析与跨店摘要是跨渠道口径，仅在全部渠道显示；清除后无法从正文恢复身份的记录只在全部身份中出现，不能猜测为用户数据。当前用户的全部记录可分状态查看，数量按店铺/身份/渠道/类型统计，与当前页长度分开。最近三条实际 Agent/运营运行遵从店铺/身份/渠道范围，展示实际步骤或新增/复用候选和已有数据截至说明；没有运行时不造占位任务。

联合查询按创建时间、类型、ID 三项倒序翻页，每次最多读取 21 条以返回 20 条及下一游标。游标包含边界和筛选摘要，换范围必须重新加载；游标不授予权限。总数与列表在同一请求数据库快照读取，页面不把记录创建时间称为最近修改时间。不同请求之间有新处理或来源变化时，刷新回到最新状态；“加载更早”按创建边界继续。

### 状态与权限

来源有效性以持久失效标记、库存有效期、客服引用政策起止点和当前经营规则版本联合投影。R1 状态核对撤销、期限、来源版本/有效期、规则版本和剩余次数；R2 入口仍指向原邮件全文、独立审批和回执。Agent 模型租约到期与邮件提交超 60 秒按已有业务门禁呈现未知；未知优先于来源需更新，避免用户错过应核对的外部结果。

首页 GET 不写数据库、不推进步骤、不请求模型或供应商。每项操作打开原业务页面，服务端在实际动作时重新核对对象、版本、来源和授权。列表中的状态不是执行凭证。R1 仅保存内部候选，邮件继续使用 R2 门禁；来源清除后不返回业务标签和摘要正文，仍可看无正文历史或未知回执入口。

`WorkInbox.vue` 沿用现有绿色 tokens，提供状态计数、筛选、实际运行摘要、分卡事项和空状态。请求序号丢弃切换范围后的迟到响应及错误，窗口 focus 刷新会清除旧列表。原业务页支持携带 shop 与确切对象 ID 的深链；路由 query 改变重新挂载页面。`deepLink.ts` 验证正整数和店铺归属，无权店铺显示错误。R1 指定授权即使不在首个历史页也独立读取并展开。所有导入文字通过 Vue 文本插值显示。

### 分析核对待办的可处理状态

原 `AnalysisTodo` 只有创建入口。迁移 `86df84dc129a` 增加 version 列，已有记录从 1 开始；`AnalyticsService.change_todo` 复用用户→店铺锁、FOR UPDATE 与 populate_existing。完成/重开携带期望版本，来源必须有效；重复相同目标安全回读，完成→重开后旧版本不能再次完成。状态、版本和无正文审计同事务提交，审计失败整体回滚。

分析页显示确切分析/待办 ID、状态和版本，可标记核对完成或重开。完成记录遇新导入时保留 completed，关联分析仍标 stale，避免把已做工作改成未处理；未完成记录沿用 stale，清除仍擦除标题及关联分析正文并增加版本。状态表示卖家的核对进度，不宣称缺失费用已补全或经营结论已被验证。
